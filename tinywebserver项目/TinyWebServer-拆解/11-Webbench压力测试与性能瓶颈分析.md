# Webbench压力测试与性能瓶颈分析

返回：[[TinyWebServer-面试拆解笔记]]

相关：[[TinyWebServer-拆解/05-线程池与并发模型]]、[[TinyWebServer-拆解/09-静态资源、项目亮点与面试表达]]、[[TinyWebServer-面试问答模拟版]]

> [!abstract]
> 这篇专门讲 4 件事：
> 1. Webbench 是什么
> 2. 如何对 TinyWebServer 做压力测试
> 3. 压测时看哪些指标
> 4. 如何根据测试结果分析服务端性能瓶颈

## 1. 什么是 Webbench

Webbench 是一个轻量级 Web 压力测试工具。  
它的目标很直接：

- 模拟多个客户端同时访问服务器
- 在一定时间内持续发送 HTTP 请求
- 统计服务器能处理多少请求、传输了多少数据、失败了多少次

一句话理解：

> Webbench 就是“用程序批量模拟很多个浏览器去打你的服务器，然后统计服务器扛住了多少请求”。

## 2. Webbench 在这个项目里为什么合适

这个项目本身就是一个轻量级 HTTP 服务器，核心关注的是：

- 并发连接处理能力
- I/O 模型差异
- 线程池调度能力
- 日志、数据库连接池、定时器等附加模块对性能的影响

而 Webbench 正好擅长测：

- 高并发 HTTP 请求吞吐
- 不同配置下的请求处理效率
- 同一服务在不同参数下的相对差异

也就是说，它非常适合做这个项目的“并发性能对比实验”。

## 3. Webbench 的工作原理是什么

从 `webbench.c` 的实现可以看出，它的大致流程是：

1. 解析命令行参数
2. 构造 HTTP 请求字符串
3. 启动多个并发客户端进程
4. 每个客户端不断向目标服务器发起请求
5. 在设定时间内持续循环
6. 统计：
   - 成功请求数
   - 失败请求数
   - 传输字节数
7. 最后汇总结果并输出

## 4. 它本质上在测什么

本质上测的是：

- 服务器单位时间内能完成多少 HTTP 请求
- 服务器在一定并发下是否稳定
- 在请求持续打满时，哪些模块开始成为瓶颈

所以它不只是“跑个数字”，而是在帮你回答：

- 这个服务器快不快
- 稳不稳
- 卡在哪里

## 5. 常用命令参数是什么

项目自带说明里最常见的形式是：

```bash
./webbench -c 500 -t 30 http://127.0.0.1/index.html
```

常用参数：

- `-c`
  并发客户端数
- `-t`
  压测持续时间，单位秒

从 `webbench.c` 里还能看到一些扩展参数：

- `-f` / `--force`
  不等待服务器响应，适合测极限发送能力
- `-r` / `--reload`
  强制重新加载
- `-9`
  使用 HTTP/0.9
- `-1`
  使用 HTTP/1.0
- `-2`
  使用 HTTP/1.1
- `--get`
  GET 请求
- `--head`
  HEAD 请求
- `--options`
  OPTIONS 请求
- `--trace`
  TRACE 请求

不过在这个项目里，面试最常讲的是：

- `-c` 并发量
- `-t` 持续时间

## 6. 对 TinyWebServer 怎么做压力测试

## 6.1 第一步：先启动服务器

例如：

```bash
./server
```

或者按指定参数启动：

```bash
./server -p 9006 -l 0 -m 3 -o 1 -s 8 -t 8 -c 1 -a 0
```

这里建议压测前先明确好你要测的维度，比如：

- Reactor 还是 Proactor
- LT 还是 ET
- 是否开启日志
- 线程数多少
- 数据库连接池大小多少

## 6.2 第二步：尽量减少干扰因素

为了得到更纯粹的服务器吞吐数据，通常会：

- 关闭日志
- 选一个稳定的静态资源地址
- 保证服务器和压测环境尽量稳定

原因是：

- 日志会引入额外磁盘 I/O
- 动态业务可能引入数据库波动
- 文件大小不同也会显著影响吞吐

## 6.3 第三步：运行 Webbench

例如：

```bash
webbench -c 500 -t 30 http://127.0.0.1:9006/judge.html
```

表示：

- 同时模拟 500 个客户端
- 连续压 30 秒
- 持续请求 `judge.html`

## 6.4 第四步：记录结果

你需要重点记录：

- 并发数
- 压测时长
- 请求资源类型
- 服务器启动参数
- 测试输出结果

如果只是记一个“QPS 很高”，面试时其实不好用。  
真正有说服力的是：

> 在某种参数组合下，用多少并发、压多久、请求什么资源、最终得到什么结果。

## 7. 压测时最重要的指标是什么

## 7.1 吞吐量 / 请求率

最常见的就是：

- QPS
  每秒请求数
- pages/min
  每分钟处理页面数

它表示：

- 单位时间内服务器完成了多少个请求

这个指标最能反映整体吞吐能力。

## 7.2 数据传输速率

例如：

- bytes/sec

它表示：

- 服务器每秒传输了多少字节的数据

这个指标在返回静态大文件时尤其重要。

## 7.3 成功请求数

表示：

- 服务器成功完成了多少请求

如果吞吐很高但成功率不高，那说明结果并不好。

## 7.4 失败请求数

表示：

- 建连失败
- 请求超时
- 收发异常
- 服务端崩溃或拒绝响应

这个指标对稳定性很重要。

## 7.5 并发客户端数

这个不是结果指标，而是实验条件。

比如：

- `-c 100`
- `-c 500`
- `-c 1000`

你要看的是：

- 随着并发增加，吞吐怎么变化
- 失败率是否上升
- 是否出现明显拐点

## 8. 项目里给出的压测结果说明了什么

README 里给了多组结果，对比的是：

- Reactor / Proactor
- LT / ET 的不同组合

它本质上在说明：

- 不同事件处理模型对吞吐有影响
- 不同触发模式组合对性能也有影响

这个很适合面试里说：

> 我不是只跑了一次压测，而是把服务器的不同并发模型配置拆开做了对比，这样能更清楚地看到系统设计对吞吐的影响。

## 9. 为什么不同配置下性能会不同

因为服务器的性能不是单一因素决定的，而是多模块共同作用的结果。

比如：

- LT 和 ET 模式对读写次数和事件触发频率有影响
- Reactor 和 Proactor 模式会影响主线程和工作线程的职责分配
- 日志开关会影响磁盘 I/O
- 线程池大小会影响任务并发处理能力
- 数据库连接池大小会影响数据库访问等待

所以压测本质上是在验证：

> 你的架构设计在真实高并发下表现怎样。

## 10. 如何根据压测结果分析性能瓶颈

这部分是面试最有价值的内容。

不要只会说：

- “QPS 是多少”

要会说：

- “QPS 为什么到这里上不去了”
- “失败率为什么升高”
- “瓶颈更像是 CPU、网络、磁盘，还是锁竞争”

## 10.1 如果并发增加，但 QPS 不再增长

可能说明：

- CPU 已经打满
- 线程池线程数不足
- 锁竞争严重
- 主线程 epoll 分发能力成为瓶颈

结合这个项目，常见怀疑点包括：

- 线程池任务处理跟不上
- `http_conn` 解析和响应构造耗时
- Reactor 模式下工作线程读写开销大

## 10.2 如果失败请求数开始明显增加

可能说明：

- fd 上限不够
- 监听队列太小
- 线程池积压严重
- 数据库连接池不够用
- 服务端响应不及时导致客户端超时

结合这个项目，还可能是：

- 定时器频繁关闭连接
- ET 模式读写处理不当
- 资源耗尽

## 10.3 如果吞吐高，但 bytes/sec 不高

说明：

- 请求可能都是小页面
- 服务器擅长处理轻量请求

这时候更像是在测：

- 调度能力
- 请求解析能力

而不是大文件传输能力。

## 10.4 如果 bytes/sec 很高，但 QPS 不一定高

说明：

- 请求可能是大文件
- 网络带宽或文件发送路径可能成为瓶颈

在这个项目里，这种情况下要重点怀疑：

- `mmap + writev` 路径表现
- 网络带宽
- 内核发送缓冲区

## 10.5 如果关闭日志后性能明显提升

说明：

- 日志 I/O 是明显瓶颈
- 磁盘写入拖慢了主流程

这正好可以说明：

- 为什么异步日志有意义

## 10.6 如果调大线程池后吞吐先升后降

说明：

- 线程数太少时并发不足
- 线程数太多时上下文切换和锁竞争增加

这意味着线程池不是越大越好。

## 10.7 如果涉及登录注册，请求一多就变慢

说明：

- 数据库连接池可能不够
- 数据库本身可能成为瓶颈
- 业务逻辑比静态文件请求更重

所以压测时最好区分：

- 静态资源测试
- 动态业务测试

## 11. 这个项目里最可能的瓶颈有哪些

按模块来分析，常见瓶颈可以这样拆。

## 11.1 主线程事件分发瓶颈

主线程要负责：

- `accept`
- `epoll_wait`
- 事件判断
- 分发任务

如果连接太多、事件太频繁，主线程可能先顶不住。

## 11.2 线程池处理瓶颈

如果工作线程数过少：

- 任务排队
- 响应延迟升高

如果工作线程过多：

- 上下文切换增多
- 锁竞争变多

## 11.3 锁竞争瓶颈

这个项目里多个地方都有锁：

- 线程池任务队列
- 日志系统
- 数据库连接池

高并发下锁竞争会拖慢吞吐。

## 11.4 数据库瓶颈

一旦请求进入登录注册流程，就不只是静态文件了。  
这时可能受限于：

- 数据库连接池大小
- MySQL 响应速度
- SQL 执行效率

## 11.5 网络和文件发送瓶颈

如果请求图片或视频文件，压力会更多落在：

- 网络带宽
- 文件发送路径
- 内核缓冲区

## 11.6 日志 I/O 瓶颈

如果开启同步日志：

- 每个请求都要写盘
- 很容易拖慢吞吐

## 12. 压测时应该怎么设计实验才更像工程分析

建议至少做下面几组对比。

### 对比 1：开日志和关日志

看日志系统是否成为瓶颈。

### 对比 2：Reactor 和 Proactor

看不同事件处理模型的吞吐差异。

### 对比 3：LT 和 ET

看不同触发模式组合的性能表现。

### 对比 4：不同线程数

比如：

- 4 线程
- 8 线程
- 16 线程

找最合适的线程池规模。

### 对比 5：静态请求和动态请求

把：

- 请求 html
- 请求登录注册

分开压测，区分网络瓶颈和数据库瓶颈。

## 13. 压测结果该怎么表达才像面试回答

不要只说：

> 我用 Webbench 测过，QPS 很高。

更好的说法是：

> 我用 Webbench 对服务器做过并发压测，主要从并发客户端数、压测持续时间、请求类型和服务器启动参数四个维度记录实验条件，再重点观察 QPS、字节吞吐和失败请求数。通过对比不同的 Reactor/Proactor、LT/ET 和日志开关配置，我能看到不同架构设计对吞吐的影响，并进一步分析是主线程分发、线程池调度、数据库访问还是日志 I/O 成为了性能瓶颈。

## 14. 你可以直接背的一段话

> Webbench 是一个轻量级 HTTP 压力测试工具，它通过模拟多个并发客户端在一定时间内持续向服务器发送请求，统计每秒请求数、数据吞吐量以及成功失败次数。我在这个项目里主要用它来对比不同并发模型和触发模式下的性能差异，比如 Reactor 和 Proactor、LT 和 ET 组合。压测时我会先固定请求资源和服务器参数，再观察 QPS、bytes/sec 和失败请求数这些指标。如果并发升高后 QPS 不再增长，通常说明 CPU、线程池或锁竞争到了瓶颈；如果失败数开始上升，通常说明 fd、线程池、数据库连接池或响应延迟出现了问题。这样压测的意义就不只是跑一个数字，而是帮助定位服务端的真实瓶颈。

## 16. 本次 ET + ET 压测结果分析

这次 ET + ET 模式下，请求的是：

```text
GET http://localhost:9007/
```

压测时间统一是 5 秒，结果整理成表：

| 并发客户端数 | 成功请求数 | 失败请求数 | QPS 约等于 | bytes/sec |
|---:|---:|---:|---:|---:|
| 500 | 32393 | 0 | 6479 | 725580 |
| 1000 | 31651 | 0 | 6330 | 708982 |
| 2000 | 31120 | 0 | 6224 | 697110 |
| 4000 | 28233 | 0 | 5647 | 632352 |
| 6000 | 28330 | 0 | 5666 | 634569 |
| 8000 | 27801 | 0 | 5560 | 622742 |

### 先说结论

这组数据说明：

> 在当前机器和当前 Webbench 测试方式下，服务器的有效吞吐上限大约已经在 `5600 ~ 6500 QPS` 这一档。  
> 并发客户端数从 500 增加到 8000，并没有带来更多成功请求，说明瓶颈已经不在“客户端数量够不够”，而在“服务端或本机压测环境单位时间最多能完成多少请求”。

也就是说，`requests` 几乎不再增长不是异常，而是进入了吞吐平台期。

### 为什么 client 数增加，requests 没有明显增加

Webbench 的并发客户端数表示“同时有多少客户端在压服务器”，但服务器最终能完成多少请求，取决于这条链路里最慢的一环：

```text
Webbench 客户端进程
    -> TCP 连接建立
    -> 服务端 accept
    -> epoll 事件分发
    -> read_once 读请求
    -> 线程池 / process 处理
    -> process_write 组织响应
    -> writev 回写
    -> close 或 keep-alive 处理
```

当 500 个客户端已经足够把服务器打满时，再增加到 1000、2000、4000、8000 个客户端，只会让更多请求排队、等待调度、抢 CPU，不会凭空增加服务端处理能力。

所以这组数据的核心现象是：

```text
并发数增加
    -> 压力更大
    -> 但服务端处理能力已经到顶
    -> 成功请求数不再增长
    -> 高并发下还会因为调度和连接管理开销变大而略微下降
```

### 为什么高并发反而略微下降

从 500 clients 到 8000 clients，QPS 从大约 `6479` 降到 `5560`。  
这说明高并发没有让服务器更快，反而引入了额外开销。

最可能的原因有几个：

1. **本机压测导致客户端和服务端抢 CPU**

   这次请求的是 `localhost:9007`，说明 Webbench 和 TinyWebServer 很可能跑在同一台机器上。  
   Webbench 本身会创建大量客户端进程/连接，它也需要 CPU 调度。

   当 clients 很大时，CPU 不只在跑服务器，还要跑大量 Webbench 客户端。  
   所以测到的不是纯服务端性能，而是：

   ```text
   服务端处理能力 + Webbench 发压能力 + 操作系统调度能力
   ```

   这会让高并发下的 QPS 下降。

2. **短连接场景下，连接建立和关闭开销很重**

   Webbench 默认更像是在不断制造 HTTP 请求压力。  
   如果每个请求都伴随连接建立、accept、epoll 注册、回收连接，那么服务器大量时间会花在：

   - `accept`
   - `epoll_ctl`
   - 定时器添加 / 删除
   - socket 关闭
   - 连接对象初始化

   对 TinyWebServer 这种项目来说，请求 `/` 返回的内容很小，真正业务处理并不重。  
   这时瓶颈很可能不在 HTTP 解析本身，而在大量短连接带来的系统调用和事件管理开销。

3. **主线程事件分发可能成为瓶颈**

   TinyWebServer 虽然有线程池，但主线程仍然负责：

   - `epoll_wait`
   - 新连接 `accept`
   - 事件判断
   - 读写事件分发
   - 定时器和信号事件处理

   当连接数升高时，主线程要处理的事件数量会增加。  
   如果主线程的事件分发速度到了上限，线程池再多也不一定能继续提高 QPS。

4. **ET 模式降低重复通知，但要求一次读/写尽**

   ET + ET 的优势是减少重复事件通知。  
   但它也要求代码在可读或可写时尽可能循环读完、写完。

   在高并发短连接压测下，ET 模式不一定总比 LT 更高，因为性能还取决于：

   - 每次事件里处理了多少连接
   - `read_once()` / `write()` 是否频繁遇到 `EAGAIN`
   - `epoll_ctl` 修改事件的次数
   - 主线程是否被大量连接事件拖住

   所以 ET + ET 没有随 clients 增加而继续上涨，是可以理解的。

### 这是不是网络带宽瓶颈

不像。

因为最高 `bytes/sec` 只有大约：

```text
725580 bytes/sec ≈ 0.69 MB/s
```

这个吞吐量很小，远远不像网卡带宽瓶颈。  
而且本次访问的是 `localhost`，走的是本机回环网络，网络带宽通常不是主要限制。

所以这次更像是：

```text
CPU 调度 + 短连接系统调用 + epoll 事件分发 + 连接管理
```

这些共同限制了 QPS。

### 这是不是数据库瓶颈

不像。

这次请求的是：

```text
GET /
```

如果只是访问首页或静态资源，一般不会进入登录注册的 MySQL 查询逻辑。  
所以这组数据不适合说明数据库连接池瓶颈。

如果要测数据库瓶颈，应该单独压：

```text
POST /2CGISQL.cgi
POST /3CGISQL.cgi
```

也就是登录和注册流程。

### 这是不是日志瓶颈

要看压测时有没有关闭日志。

如果日志开启，并且每个请求都写日志，那么日志系统可能参与瓶颈。  
尤其是同步日志或频繁 `flush()` 时，磁盘 I/O 和锁竞争会拖慢请求处理。

但从这组数据本身看，0 failed 且 bytes/sec 很低，更明显的问题还是吞吐平台期。  
后续可以做一组对比：

```text
关闭日志压一次
开启同步日志压一次
开启异步日志压一次
```

如果关闭日志后 QPS 明显上升，才说明日志 I/O 是主要瓶颈。

### 这组数据最合理的判断

这组 ET + ET 压测里，最合理的判断是：

> 500 clients 时已经基本打满当前环境的处理能力。  
> 之后继续增加到 1000、2000、4000、6000、8000 clients，并不会提高服务端处理速度，反而会增加客户端进程调度、连接建立关闭、epoll 事件分发和定时器维护的额外开销。  
> 所以成功请求数基本稳定在 2.8 万到 3.2 万之间，高并发时略有下降，但 0 failed 说明服务器没有崩溃，稳定性还可以。

一句话概括：

> 这不是“并发没压上去”，而是“500 并发已经把当前服务器和本机压测环境压到吞吐上限了”。

### 面试时可以怎么说

如果面试官问：“为什么 500、1000、8000 并发下请求数差不多？”

可以这样答：

> 我这组 ET + ET 压测里，500 并发时已经达到 6400 左右 QPS，后续把并发加到 8000，请求数没有继续增长，说明瓶颈已经不在客户端并发数，而在当前环境下服务端单位时间处理请求的能力。因为这次是 localhost 压测，Webbench 客户端和服务器会抢同一台机器的 CPU；同时 Webbench 的短连接压力会带来大量 accept、epoll_ctl、连接初始化、定时器维护和关闭 socket 的系统调用开销。所以高并发下 QPS 反而略有下降。由于失败数一直是 0，说明服务器稳定性可以，但吞吐已经进入平台期。下一步我会通过关闭日志、换独立压测机、观察 CPU 占用和系统调用次数来进一步确认瓶颈。

### 后续怎么验证瓶颈

可以继续做几组实验：

1. **服务器和 Webbench 分开机器跑**

   排除本机客户端和服务端抢 CPU 的影响。

2. **固定 500 clients，延长压测时间**

   比如从 5 秒改成 30 秒，观察 QPS 是否稳定。

3. **分别压小文件、大文件、登录接口**

   区分：

   - 小文件：偏连接和事件分发瓶颈
   - 大文件：偏写回和带宽瓶颈
   - 登录注册：偏数据库连接池和 SQL 瓶颈

4. **对比日志开关**

   如果关闭日志后 QPS 明显提升，说明日志 I/O 或日志锁竞争影响较大。

5. **观察 CPU 和系统调用**

   可以重点看：

   - CPU 是否打满
   - 上下文切换是否很多
   - `accept` / `epoll_ctl` / `read` / `writev` 调用是否很密集
   - 服务端主线程是否比工作线程更忙

这样才能把“QPS 不再增长”从现象进一步定位到具体瓶颈。
