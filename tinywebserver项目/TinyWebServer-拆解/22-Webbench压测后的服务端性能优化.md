## 这篇笔记讲什么

这篇用来回答简历里这句话：

> 使用 Webbench 进行压力测试，并结合测试结果分析服务端性能瓶颈。

面试时不要只说“CPU 瓶颈”，那样听起来像只是跑了一个测试结果。更好的表达是：

> 我先用 Webbench 做不同并发下的吞吐测试，发现 QPS 在 500 clients 左右进入平台期，继续增大并发并没有带来吞吐提升。然后我结合访问资源、失败数、bytes/sec 和源码路径分析，排除了网络带宽和数据库瓶颈，把重点放在短连接系统调用、epoll 事件分发、连接管理和日志热路径上。最后我选了一个可以直接落地的优化点：减少请求热路径上的高频日志和强制刷盘，降低业务线程在日志锁和磁盘 I/O 上的耗时。

---

## 压测现象怎么说

可以这样组织：

1. 我用 Webbench 访问静态页面，例如 `judge.html`。
2. 固定压测时间，逐步增加并发数，例如 `500 -> 1000 -> 2000 -> 4000 -> 8000`。
3. 观察到并发数继续增加后，成功请求数没有线性增长，而是进入平台期。
4. 失败数基本为 0，说明服务器稳定性还可以，不是因为崩溃导致吞吐上不去。
5. `bytes/sec` 并不高，而且访问的是本机 `localhost`，所以不像网络带宽瓶颈。
6. 请求的是静态资源，没有走登录注册 SQL，所以也不像数据库瓶颈。

最后给出判断：

> 这组压测更像是服务端在小文件短连接场景下进入吞吐平台期，主要开销集中在连接建立关闭、`accept`、`epoll_ctl`、事件分发、HTTP 解析、响应拼接以及日志系统这些高频路径上。

---

## 为什么选择日志热路径做优化

源码里有一个非常适合优化的点：日志调用出现在请求处理热路径里。

### 1. HTTP 解析阶段逐行打印

原来 `process_read()` 每解析一行请求行或请求头，就会打印一次：

```cpp
LOG_INFO("%s", text);
```

一个普通 GET 请求至少有请求行、Host、Connection 等多行头部。Webbench 一压就是几万次请求，这里会产生大量 INFO 日志。

### 2. 响应拼接阶段反复打印

原来 `add_response()` 每拼一段响应内容，也会打印当前响应缓冲区：

```cpp
LOG_INFO("request:%s", m_write_buf);
```

而一个响应不是一次拼完的，通常会依次追加：

- 状态行
- `Content-Length`
- `Connection`
- 空行
- 响应体

这意味着一次请求可能在响应拼接阶段触发多次日志。

### 3. 日志宏每条都会 flush

原来的日志宏是：

```cpp
#define LOG_INFO(format, ...) \
    if(0 == m_close_log) { \
        Log::get_instance()->write_log(1, format, ##__VA_ARGS__); \
        Log::get_instance()->flush(); \
    }
```

也就是说，即使配置了异步日志，业务线程每写一条 INFO 也会调用 `flush()`。这会带来：

- 日志对象互斥锁竞争
- 文件流强制刷新
- 业务线程被日志路径拖慢
- Webbench 压测时大量请求都被日志开销放大

所以这不是“为了优化而优化”，而是从压测现象回到源码后能看到的真实热点。

---

## 我做了什么修改

### 修改 1：去掉 HTTP 解析热路径逐行 INFO 日志

原逻辑：

```cpp
text = get_line();
m_start_line = m_checked_idx;
LOG_INFO("%s", text);
```

优化后：

```cpp
text = get_line();
m_start_line = m_checked_idx;
// 压测时不在 HTTP 解析热路径逐行打印，避免日志锁和刷盘影响吞吐。
```

这样做的含义是：

- 解析逻辑不变
- 状态机行为不变
- 只去掉高频调试日志
- 减少每个请求在日志系统上的额外开销

### 修改 2：去掉响应拼接阶段的高频 INFO 日志

原逻辑：

```cpp
m_write_idx += len;
va_end(arg_list);

LOG_INFO("request:%s", m_write_buf);

return true;
```

优化后：

```cpp
m_write_idx += len;
va_end(arg_list);

return true;
```

这样可以避免每追加一次响应头都打印一遍当前缓冲区。

### 修改 3：调整日志宏的刷盘策略

原来 `DEBUG / INFO / WARN / ERROR` 都会每条日志立即 `flush()`。

优化后：

```cpp
#define LOG_DEBUG(format, ...) if(0 == m_close_log) {Log::get_instance()->write_log(0, format, ##__VA_ARGS__);}
#define LOG_INFO(format, ...)  if(0 == m_close_log) {Log::get_instance()->write_log(1, format, ##__VA_ARGS__);}
#define LOG_WARN(format, ...)  if(0 == m_close_log) {Log::get_instance()->write_log(2, format, ##__VA_ARGS__);}
#define LOG_ERROR(format, ...) if(0 == m_close_log) {Log::get_instance()->write_log(3, format, ##__VA_ARGS__); Log::get_instance()->flush();}
```

这个设计的理由是：

- `DEBUG / INFO / WARN` 属于常规运行日志，不需要每条立刻落盘。
- `ERROR` 可能用于排查崩溃或严重错误，所以保留强制刷新。
- 如果开启异步日志，普通日志先进入阻塞队列，由后台线程写入。
- 如果是同步日志，也交给 C 标准库文件缓冲减少频繁系统调用。

---

## 这条优化怎么体现工作量

它不是只调了一个启动参数，而是走了一条完整链路：

```text
Webbench 压测
    -> 发现 QPS 进入平台期
    -> 根据 failed / bytes/sec / 静态资源访问排除崩溃、网络、数据库瓶颈
    -> 回到源码检查请求处理热路径
    -> 发现 HTTP 解析、响应拼接、日志 flush 都在每个请求上高频执行
    -> 去掉热路径调试日志
    -> 调整 INFO 日志刷盘策略
    -> 保留 ERROR flush，兼顾性能和可排查性
```

这条线比单纯说“CPU 瓶颈”更好，因为它体现了：

- 会用压测工具
- 会看指标
- 会排除不相关瓶颈
- 能回到源码定位热点路径
- 能做低风险优化
- 能说明优化取舍

## 面试时可以这样回答

如果面试官问：

> 你做了什么服务端性能优化？

可以回答：

> 我先用 Webbench 对静态资源访问做了压测，逐步提高 clients 数量后发现 QPS 在 500 clients 左右进入平台期，继续提高并发后成功请求数没有明显增长，但 failed 基本为 0。因为这次压的是静态页面，bytes/sec 也不高，所以我判断主要不是数据库或网络瓶颈，而是高并发短连接下的事件分发、连接管理和请求处理热路径开销。
>
> 后面我回到源码看了一遍请求处理链路，发现 HTTP 状态机解析每一行请求头都会打印 INFO 日志，响应拼接函数每追加一段响应也会打印一次，而且原来的日志宏对 DEBUG、INFO、WARN、ERROR 都会每条日志立即 flush。Webbench 高并发时，这会把大量业务线程时间消耗在日志锁竞争和文件刷盘上。
>
> 所以我做了一个低风险优化：去掉 HTTP 解析和响应拼接热路径上的调试日志，同时调整日志刷盘策略，让 DEBUG、INFO、WARN 走普通缓冲或异步队列，只保留 ERROR 级别立即 flush。这样核心请求处理逻辑不变，但减少了每个请求的额外日志开销。
>
> 这个优化的重点不是改变业务逻辑，而是把压测场景下的高频非必要开销从请求路径上移除，让工作线程更多时间用在真正的读写、解析和响应发送上。

---

## 面试官追问：为什么不直接说关闭日志

可以这样答：

> 关闭日志只是测试参数，不算真正的代码优化。我做的是把日志系统区分成“调试观测”和“线上运行”两种场景。请求行、响应拼接这种高频日志更适合调试阶段使用，不适合压测或高并发运行时默认打开；同时普通 INFO 日志没有必要每条都强制刷盘，ERROR 才需要更强的实时性。所以我保留了错误日志的即时性，但降低了普通日志对吞吐的影响。

这个回答听起来会比“我把日志关了”更像工程优化。

---

## 面试官追问：这个优化一定能提升 QPS 吗

不要说绝对话，可以这样答：

> 是否提升取决于压测时日志是否开启，以及磁盘和锁竞争是否明显。如果完全关闭日志，这个优化影响不会很大；但如果日志开启，尤其是同步日志或者频繁 flush，这个优化会明显减少请求热路径的额外开销。我当时选择这个点，是因为它风险低、改动范围小，而且和 Webbench 压测下的高频请求场景高度相关。

这个回答更稳，因为它不会把优化效果说死。
