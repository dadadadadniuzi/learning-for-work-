# 15-信号处理与管道转发机制

- [[TinyWebServer-面试拆解笔记]]

## 这篇笔记解决什么问题

这篇笔记专门解释这几个问题：

1. `SIGALRM`、`SIGTERM` 这些信号是谁发出来的
2. 收到信号后为什么不直接在信号处理函数里做复杂逻辑
3. 为什么要用一对管道 `m_pipefd[0] / m_pipefd[1]`
4. 主线程是怎么在 `epoll` 里统一处理信号的
5. 整个过程中每一步关键变量分别是什么值

---

## 先说结论：为什么要把信号写进管道

一句话概括：

> 因为信号是异步打断进程的，而 `epoll` 事件循环是同步主线。这个项目把“异步信号”转成“管道可读事件”，这样主线程就能像处理普通 socket 一样统一处理。

如果不这么做，会有两个麻烦：

1. 信号处理函数里不能安全做太复杂的事情
2. 服务器主循环本来就在 `epoll_wait()` 阻塞，如果信号来了但没有融入事件循环，控制流会比较乱

所以作者用了一个很常见的技巧：

- 信号处理函数只做一件极小的事：把信号编号写进管道
- 主线程把管道读端加入 `epoll`
- 一旦有信号，`epoll_wait()` 就会像发现“普通 fd 可读”一样醒来

这就把：

`异步信号 -> 同步文件描述符事件`

统一起来了。

## 涉及到的关键对象

### `m_pipefd[2]`

在 `WebServer::eventListen()` 里创建：

```cpp
socketpair(PF_UNIX, SOCK_STREAM, 0, m_pipefd);
```

它会得到一对互相连通的本地 socket。（实际上并非管道，只是当管道用）

通常可以理解成：

- `m_pipefd[0]`：读端
- `m_pipefd[1]`：写端

这个项目后面就是这么用的。

### `Utils::u_pipefd`

这是一个全局静态指针，最终指向 `m_pipefd`。

目的是：

让静态信号处理函数 `Utils::sig_handler(int sig)` 也能拿到那对管道。

因为静态函数不能直接访问某个 `WebServer` 实例的成员变量。

### `timeout`

在 `eventLoop()` 里定义：

```cpp
bool timeout = false;
```

如果主线程发现收到的是 `SIGALRM`，就把它设成 `true`。

含义是：

> 这一轮事件处理结束后，要执行一次超时连接扫描

### `stop_server`

在 `eventLoop()` 里定义：

```cpp
bool stop_server = false;
```

如果主线程发现收到的是 `SIGTERM`，就把它设成 `true`。

含义是：

> 主循环应该准备退出，服务器开始停机

## 服务器启动时，信号系统是怎么装起来的

发生在 `WebServer::eventListen()` 里。

### 第 1 步：创建管道对

```cpp
socketpair(PF_UNIX, SOCK_STREAM, 0, m_pipefd);
```

假设这次系统返回：

- `m_pipefd[0] = 6`
- `m_pipefd[1] = 7`

这只是举例，真实值每次可能不同。

此时变量值可以这样理解：

| 变量 | 值 | 含义 |
|---|---:|---|
| `m_pipefd[0]` | `6` | 读端 |
| `m_pipefd[1]` | `7` | 写端 |

### 第 2 步：把写端设成非阻塞

```cpp
utils.setnonblocking(m_pipefd[1]);
```

原因是：

信号处理函数里不能因为写管道被堵住而卡死。

### 第 3 步：把读端注册进 epoll

```cpp
utils.addfd(m_epollfd, m_pipefd[0], false, 0);
```

这一步之后，`epoll` 会关注：

> 管道读端什么时候变成“可读”

只要写端写入了数据，读端就会触发 `EPOLLIN`。

### 第 4 步：安装信号处理函数

```cpp
utils.addsig(SIGPIPE, SIG_IGN);
utils.addsig(SIGALRM, utils.sig_handler, false);
utils.addsig(SIGTERM, utils.sig_handler, false);
```

含义分别是：

- `SIGPIPE`：忽略
- `SIGALRM`：交给 `sig_handler`
- `SIGTERM`：交给 `sig_handler`

### 第 5 步：把全局静态指针指过去

```cpp
Utils::u_pipefd = m_pipefd;
Utils::u_epollfd = m_epollfd;
```

这样以后静态函数里就能用：

```cpp
u_pipefd[1]
```

往管道写信号编号了。

### 第 6 步：启动第一次闹钟

```cpp
alarm(TIMESLOT);
```

如果 `TIMESLOT = 5`，意思就是：

> 5 秒后，内核给当前进程发一个 `SIGALRM`

## `sig_handler(int sig)` 到底干了什么

源码是：

```cpp
void Utils::sig_handler(int sig)
{
    int save_errno = errno;
    int msg = sig;
    send(u_pipefd[1], (char *)&msg, 1, 0);
    errno = save_errno;
}
```

这个函数非常短，核心只有三件事。

### 第 1 件事：保存 `errno`

```cpp
int save_errno = errno;
```

原因是：

信号是异步打断当前代码执行的。

如果被打断前，主线程或者工作线程的 `errno` 里正好存着别的系统调用错误码，我们不想把它污染掉。

举例：

假设信号发生前：

```cpp
errno = 11;   // EAGAIN
```

那么这里：

| 变量 | 值 |
|---|---:|
| `errno` | `11` |
| `save_errno` | `11` |

### 第 2 件事：把信号编号放到 `msg`

```cpp
int msg = sig;
```

如果这次来的是 `SIGALRM`，通常在 Linux 下它的值是 `14`。

如果是 `SIGTERM`，通常是 `15`。

所以这里可能是：

| 信号 | `sig` | `msg` |
|---|---:|---:|
| `SIGALRM` | `14` | `14` |
| `SIGTERM` | `15` | `15` |

### 第 3 件事：把信号编号写进管道

```cpp
send(u_pipefd[1], (char *)&msg, 1, 0);
```

注意这里写的是：

```cpp
1
```

也就是只写 1 个字节。

因为这里作者只关心“小整数信号编号”，1 个字节足够装下 `14`、`15` 这种值。

写完之后，管道里就多了一个字节，比如：

- `0x0E` 表示 `SIGALRM`
- `0x0F` 表示 `SIGTERM`

这会导致：

> `m_pipefd[0]` 读端变成可读

于是 `epoll_wait()` 就会醒来。

### 第 4 件事：恢复 `errno`

```cpp
errno = save_errno;
```

这样信号处理函数就尽量不影响原来被打断的代码现场。

## 例子一：`SIGALRM` 的完整模拟流程

这个例子代表：

> 定时器时间到了，服务器需要检查有没有超时连接

### 场景初始值

假设：

- `TIMESLOT = 5`
- 当前 `eventLoop()` 正阻塞在 `epoll_wait()`
- `timeout = false`
- `stop_server = false`
- `m_pipefd[0] = 6`
- `m_pipefd[1] = 7`
- `errno = 0`

---

### 第 1 步：`alarm(5)` 到点

5 秒到了以后，内核给当前进程发送：

```text
SIGALRM
```

此时：

| 变量 | 值 |
|---|---:|
| 信号 | `SIGALRM` |
| `sig` | `14` |

---

### 第 2 步：进入 `Utils::sig_handler(14)`

进入函数时：

| 变量 | 值 |
|---|---:|
| `sig` | `14` |
| `errno` | `0` |

执行：

```cpp
int save_errno = errno;
```

之后：

| 变量 | 值 |
|---|---:|
| `save_errno` | `0` |
| `errno` | `0` |

执行：

```cpp
int msg = sig;
```

之后：

| 变量 | 值 |
|---|---:|
| `msg` | `14` |

执行：

```cpp
send(u_pipefd[1], (char *)&msg, 1, 0);
```

效果是：

- 往 fd=7 写了 1 个字节
- 字节内容是 `14`
- fd=6 变成可读

最后恢复：

```cpp
errno = save_errno;
```

于是：

| 变量 | 值 |
|---|---:|
| `errno` | `0` |

---

### 第 3 步：`epoll_wait()` 返回

因为管道读端现在可读了，所以主线程的 `epoll_wait()` 会返回。

这时事件数组里会有一个事件，对应：

```cpp
sockfd == m_pipefd[0]
```

假设：

| 变量 | 值 |
|---|---:|
| `sockfd` | `6` |
| `events[i].events` | 包含 `EPOLLIN` |

然后进入：

```cpp
dealwithsignal(timeout, stop_server);
```

---

### 第 4 步：`dealwithsignal(timeout, stop_server)`

进入函数前：

| 变量 | 值 |
|---|---:|
| `timeout` | `false` |
| `stop_server` | `false` |

定义局部变量：

```cpp
int ret = 0;
int sig;
char signals[1024];
```

这时：

| 变量 | 值 |
|---|---:|
| `ret` | `0` |
| `signals` | 未初始化 |

执行：

```cpp
ret = recv(m_pipefd[0], signals, sizeof(signals), 0);
```

因为管道里只有 1 个字节，所以：

| 变量 | 值 |
|---|---:|
| `ret` | `1` |
| `signals[0]` | `14` |

然后进入循环：

```cpp
for (int i = 0; i < ret; ++i)
```

这时：

| 变量 | 值 |
|---|---:|
| `i` | `0` |
| `signals[i]` | `14` |

命中：

```cpp
case SIGALRM:
    timeout = true;
```

于是：

| 变量 | 值 |
|---|---:|
| `timeout` | `true` |
| `stop_server` | `false` |

函数返回 `true`。

---

### 第 5 步：回到 `eventLoop()`

这一轮 `for` 循环跑完后，执行：

```cpp
if (timeout)
{
    utils.timer_handler();
    timeout = false;
}
```

因为现在：

```cpp
timeout == true
```

所以会进入 `timer_handler()`。

---

### 第 6 步：`timer_handler()` 真正处理超时

执行：

```cpp
m_timer_lst.tick();
alarm(m_TIMESLOT);
```

含义是：

1. 扫描定时器链表，把已经超时的连接关闭
2. 再约下一次 5 秒后的 `SIGALRM`

然后回到主循环，把：

```cpp
timeout = false;
```

恢复。

### 这个例子的一句话总结

`SIGALRM` 不是在信号处理函数里直接扫描超时链表，而是：

> 信号处理函数只写 1 个字节到管道，真正的超时扫描仍然回到主线程事件循环里执行。

## 例子二：`SIGTERM` 的完整模拟流程

这个例子代表：

> 外部要求服务器优雅退出

### 场景初始值

假设：

- 主线程仍在 `epoll_wait()`
- `timeout = false`
- `stop_server = false`
- `errno = 0`

---

### 第 1 步：系统发送 `SIGTERM`

比如管理员执行：

```bash
kill -TERM <pid>
```

内核就会给当前进程发送 `SIGTERM`。

通常它的值是：

| 信号 | 数值 |
|---|---:|
| `SIGTERM` | `15` |

---

### 第 2 步：进入 `sig_handler(15)`

执行过程和 `SIGALRM` 完全类似。

进入时：

| 变量 | 值 |
|---|---:|
| `sig` | `15` |
| `errno` | `0` |

执行后：

| 变量 | 值 |
|---|---:|
| `save_errno` | `0` |
| `msg` | `15` |

写入：

```cpp
send(u_pipefd[1], (char *)&msg, 1, 0);
```

于是管道读端变为可读。

---

### 第 3 步：主线程从管道读出 `15`

`dealwithsignal()` 里：

```cpp
ret = recv(m_pipefd[0], signals, sizeof(signals), 0);
```

假设结果：

| 变量 | 值 |
|---|---:|
| `ret` | `1` |
| `signals[0]` | `15` |

进入 `switch`：

```cpp
case SIGTERM:
    stop_server = true;
```

这时：

| 变量 | 值 |
|---|---:|
| `timeout` | `false` |
| `stop_server` | `true` |

---

### 第 4 步：主循环自然退出

`eventLoop()` 的最外层是：

```cpp
while (!stop_server)
```

所以本轮结束后，再回到 while 条件判断时：

```cpp
while (!true)
```

也就是：

```cpp
while (false)
```

主循环退出，服务器进入后续析构和资源释放流程。

### 这个例子的一句话总结

`SIGTERM` 的作用不是“立刻在信号函数里 exit”，而是：

> 通过管道通知主线程，把 `stop_server` 设成 `true`，让事件循环自己有序退出。

---

## 为什么不能直接在信号处理函数里做这些事

比如很多人会想：

- `SIGALRM` 来了，为什么不直接在 `sig_handler()` 里 `tick()`
- `SIGTERM` 来了，为什么不直接 `close()` 一堆 fd 然后退出

原因是：

### 原因 1：信号处理函数要尽量短小

它是异步打断执行流的。

如果里面做太多复杂逻辑，容易带来重入、安全性和时序问题。

### 原因 2：主线程本来就有完整的 epoll 事件循环

如果超时、停机、socket 读写都回到同一条主线里处理，逻辑最统一。

### 原因 3：有些操作并不适合在信号上下文里做

比如：

- 操作复杂链表
- 调用大量日志逻辑
- 统一调度连接关闭

这些都更适合回到正常线程上下文里做。

---

## 为什么这里用“管道/本地 socket 对”而不是普通全局变量

因为单纯改一个全局变量，没法唤醒正在 `epoll_wait()` 的主线程。

而写入管道后：

- 管道读端变可读
- `epoll_wait()` 立刻返回

这才真正把“信号到来”转成了“事件循环可感知的事件”。

所以这个方案同时解决了两个问题：

1. 通知主线程
2. 唤醒主线程

这就是管道方案最大的价值。

## 你面试时可以怎么回答

可以直接说：

> 这个项目把异步信号通过 `socketpair` 转成了 `epoll` 可读事件。启动时先创建一对本地 socket，把读端挂到 `epoll`，再用 `sigaction` 安装 `SIGALRM` 和 `SIGTERM` 的处理函数。真正来信号时，`sig_handler` 不做复杂逻辑，只是把信号编号写进管道写端。这样主线程阻塞在 `epoll_wait` 时也会被唤醒，然后在 `dealwithsignal()` 里统一读出信号编号：如果是 `SIGALRM`，就把 `timeout` 设为 `true`，本轮循环末尾调用 `timer_handler()` 扫描超时连接；如果是 `SIGTERM`，就把 `stop_server` 设为 `true`，让事件循环优雅退出。  

---

## 最后记住 5 个最重要的点

1. `SIGALRM` 是 `alarm(TIMESLOT)` 到点后由内核发出来的。
2. `SIGTERM` 通常是外部 `kill -TERM pid` 发出来的。
3. `sig_handler()` 只负责把信号编号写进 `u_pipefd[1]`。
4. 主线程通过 `epoll` 监听 `m_pipefd[0]`，所以能统一处理信号。
5. `SIGALRM` 最终改的是 `timeout`，`SIGTERM` 最终改的是 `stop_server`。
