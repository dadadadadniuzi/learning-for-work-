## HTTP 和 HTTPS 有什么区别

### 简要回答

HTTPS 是在 HTTP 和 TCP 之间加入 TLS/SSL，用来实现加密传输、身份认证和完整性保护。

### 对比表

| 对比点 | HTTP | HTTPS |
|---|---|---|
| 安全性 | 明文传输 | 加密传输 |
| 默认端口 | `80` | `443` |
| 证书 | 不需要 | 需要 CA 证书 |
| 身份认证 | 无法可靠确认服务器身份 | 通过证书验证服务器身份 |
| 完整性 | 容易被篡改 | TLS 可检测篡改 |
| 性能 | 少一次 TLS 握手 | 有加密和握手成本，但现代协议已优化 |

### 面试表达

> HTTPS 不只是“HTTP 加密版”，它同时解决窃听、篡改、冒充三个问题。加密保证内容不被看懂，摘要和 MAC 保证不被篡改，证书保证访问的服务器是真的。

## HTTPS 工作原理是什么

### 简要回答

HTTPS 使用非对称加密协商会话密钥，再用对称加密传输业务数据。

### 详细流程

1. 客户端和服务器先建立 TCP 连接。
2. 客户端发起 TLS 握手，发送支持的 TLS 版本、加密套件、随机数。
3. 服务器返回证书、公钥、选择的加密套件和随机数。
4. 客户端验证证书是否合法。
5. 双方通过密钥交换生成会话密钥。
6. 后续 HTTP 数据使用对称加密传输。

### 报文示意

```text
# HTTPS 默认端口
443

# 简化理解：非对称加密用于安全协商密钥，对称加密用于高效传输数据
TCP 三次握手 -> TLS 握手 -> HTTP 加密请求/响应
```

### 面试表达

> 非对称加密安全但慢，适合交换密钥；对称加密快，适合传输大量数据。所以 HTTPS 采用混合加密：握手阶段解决信任和密钥协商，传输阶段用会话密钥加密数据。

## 对称加密和非对称加密有什么区别

### 简要回答

对称加密加密和解密使用同一个密钥；非对称加密使用公钥和私钥，一把加密，另一把解密。

### 对比表

| 对比点 | 对称加密 | 非对称加密 |
|---|---|---|
| 密钥 | 同一个密钥 | 公钥 + 私钥 |
| 性能 | 快 | 慢 |
| 密钥分发 | 难点在于安全传递密钥 | 公钥可以公开 |
| HTTPS 中用途 | 加密实际传输数据 | 证书验证、密钥交换 |

### 记忆

> 对称加密像两个人共用一把钥匙，速度快但钥匙怎么安全交给对方是问题；非对称加密像公开邮箱和私人钥匙，安全性更好但计算成本高。

## 证书校验解决什么问题

### 简要回答

证书校验用于确认服务器身份，防止中间人冒充目标网站。

### 详细回答

浏览器会检查：

- 证书是否由可信 CA 签发。
- 证书域名是否和访问域名一致。
- 证书是否过期或被吊销。
- 证书链是否完整可信。

### 面试表达

> 如果只有加密没有证书，客户端可能把密钥发给攻击者。证书的作用就是让客户端确认“这个公钥确实属于我要访问的网站”。

## 强缓存和协商缓存有什么区别

### 简要回答

强缓存直接使用本地缓存，不请求服务器；协商缓存会请求服务器确认缓存是否还能用。

### 对比表

| 对比点 | 强缓存 | 协商缓存 |
|---|---|---|
| 是否请求服务器 | 不请求 | 会请求 |
| 成功状态 | `200 OK (from disk/memory cache)` | `304 Not Modified` |
| 主要字段 | `Cache-Control`、`Expires` | `ETag`、`If-None-Match`、`Last-Modified`、`If-Modified-Since` |
| 速度 | 更快 | 稍慢，但能确认资源是否变化 |

### 强缓存示例

```http
# HTTP/1.1 常用强缓存：资源 3600 秒内直接用本地缓存
Cache-Control: max-age=3600, public

# HTTP/1.0 老字段，指定绝对过期时间
Expires: Thu, 30 Feb 2025 00:00:00 GMT
```

### 协商缓存示例

```http
# 第一次响应：服务器告诉浏览器资源最后修改时间和 ETag
HTTP/1.1 200 OK
Last-Modified: Thu, 27 Feb 2025 18:06:00 GMT
ETag: "d3f4e5kamanotes"

# 下次请求：浏览器带上缓存标识，询问资源是否变化
If-Modified-Since: Thu, 27 Feb 2025 18:06:00 GMT
If-None-Match: "d3f4e5kamanotes"

# 没变化：服务器不返回响应体，浏览器继续用缓存
HTTP/1.1 304 Not Modified
```

### 常见 Cache-Control

| 指令 | 含义 |
|---|---|
| `max-age=3600` | 资源 3600 秒内有效 |
| `no-cache` | 不直接用缓存，必须先协商验证 |
| `no-store` | 不存储缓存 |
| `public` | 浏览器和代理服务器都可以缓存 |
| `private` | 只允许浏览器私有缓存 |

### 面试表达

> 强缓存看本地是否过期，没过期就不请求服务器；协商缓存会带着 ETag 或 Last-Modified 去问服务器，没变化就返回 304，节省响应体传输。

## Cookie 和 Session 有什么区别

### 简要回答

Cookie 保存在客户端，Session 保存在服务器端；Session 通常依赖 Cookie 保存 Session ID。

### 对比表

| 对比点 | Cookie | Session |
|---|---|---|
| 存储位置 | 浏览器端 | 服务器端 |
| 安全性 | 较低，容易被窃取或篡改 | 较高，数据在服务端 |
| 数据大小 | 较小 | 理论上可存复杂对象，但受服务器内存影响 |
| 生命周期 | 可设置 `Expires`、`Max-Age` | 由服务端超时控制 |
| 性能影响 | 每次请求会携带，过大会浪费带宽 | 占用服务端存储 |

### Cookie 示例

```http
# 服务器让浏览器保存 Cookie
Set-Cookie: username=kamanotes; Path=/; HttpOnly

# 浏览器后续请求会自动带上 Cookie
Cookie: username=kamanotes

# 设置 Cookie 保存 30 天
Set-Cookie: username=kamanotes; Max-Age=2592000
```

### Session 示例

```http
# 服务端创建 Session 后，把 Session ID 发给浏览器
Set-Cookie: JSESSIONID=abc123carl

# 浏览器后续带上 JSESSIONID，服务器据此找到对应 Session 数据
Cookie: JSESSIONID=abc123carl

# 如果 Cookie 被禁用，有些框架会把 Session ID 放到 URL 里，但不推荐
/path;jsessionid=abc123
```

### Cookie 安全属性

| 属性 | 作用 |
|---|---|
| `HttpOnly` | JS 不能读取，降低 XSS 窃取风险 |
| `Secure` | 只在 HTTPS 下发送 |
| `SameSite` | 限制跨站请求携带 Cookie，降低 CSRF 风险 |

### 补充

分布式系统中，Session 需要考虑共享问题，常见方案有 Redis 集中存储 Session、Session 复制、JWT 等。

### 面试表达

> Cookie 更像浏览器保存的小票，Session 是服务器保存的用户状态。登录态常见做法是 Cookie 里保存 Session ID，真正的用户信息放在服务端。
