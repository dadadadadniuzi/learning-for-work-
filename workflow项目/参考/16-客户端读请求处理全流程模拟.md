# 16-客户端读请求处理全流程模拟

## 这篇笔记讲什么

这篇笔记只做一件事：

> 模拟“客户端发来一个 HTTP 请求，服务器是怎么把它读进来并解析掉的”

我会选一个读请求例子，然后把这条链路拆成：

1. 哪个函数先收到事件
2. 它调用了哪个函数
3. 每一步关键变量是多少
4. 最后怎么进入 HTTP 状态机

---

## 例子：客户端发来一个 GET 请求

假设客户端发的是：

```http
GET /index.html HTTP/1.1
Host:127.0.0.1:9006
Connection: keep-alive

```

为了方便模拟，假设这次这个请求一次性全部到达。

这个请求大致特征是：

- 方法：`GET`
- URL：`/index.html`
- HTTP 版本：`HTTP/1.1`
- 长连接：`keep-alive`
- 没有请求体

---

## 先说明两条可能路径

`WebServer::dealwithread()` 里其实有两种并发模型：

1. `Reactor`
2. `Proactor`

这篇主模拟采用 `Proactor`，因为更好理解：

> 主线程先读 socket，再把后续处理交给线程池

最后我会补一句 Reactor 和它的区别。

---

## 时间线总览

### 整体调用链

```text
epoll_wait
-> WebServer::eventLoop()
-> WebServer::dealwithread(sockfd)
-> users[sockfd].read_once()
-> m_pool->append_p(users + sockfd)
-> threadpool::run()
-> request->process()
-> http_conn::process_read()
```

你要记住：

> 真正进入 HTTP 状态机的是 `http_conn::process_read()`，但它前面还有一整段“事件分发 + 读取 socket + 投递线程池”的过程。

---

## 第 0 步：连接刚建立时的初值

假设：

- 这个客户端对应的 fd 是 `12`
- 它的 `http_conn` 对象是 `users[12]`

在 `users[12].init(...)` 执行完后，关键变量是：

| 变量 | 值 |
|---|---:|
| `m_sockfd` | `12` |
| `m_check_state` | `CHECK_STATE_REQUESTLINE` |
| `m_read_idx` | `0` |
| `m_checked_idx` | `0` |
| `m_start_line` | `0` |
| `m_write_idx` | `0` |
| `m_linger` | `false` |
| `m_method` | 默认 `GET` |
| `cgi` | `0` |
| `bytes_to_send` | `0` |
| `bytes_have_send` | `0` |

这表示：

- 连接建立了
- 但还没有读到任何请求数据
- 也还没有开始解析

---

## 第 1 步：`epoll_wait()` 发现这个连接可读

主线程卡在：

```cpp
int number = epoll_wait(m_epollfd, events, MAX_EVENT_NUMBER, -1);
```

现在客户端把 GET 请求发过来了，于是内核会把：

```cpp
sockfd = 12
events[i].events 包含 EPOLLIN
```

返回给主线程。

此时关键变量：

| 变量 | 值 |
|---|---:|
| `sockfd` | `12` |
| `events[i].events` | `EPOLLIN` |

然后 `eventLoop()` 进入：

```cpp
dealwithread(sockfd);
```

---

## 第 2 步：进入 `WebServer::dealwithread(12)`

先拿到这个连接对应的定时器：

```cpp
util_timer *timer = users_timer[sockfd].timer;
```

假设：

| 变量 | 值 |
|---|---|
| `sockfd` | `12` |
| `timer` | 指向这个连接对应的超时定时器 |

如果当前是 `Proactor` 模式，会走：

```cpp
if (users[sockfd].read_once())
```

---

## 第 3 步：进入 `http_conn::read_once()`

### 进入前变量

| 变量 | 值 |
|---|---:|
| `m_sockfd` | `12` |
| `m_read_idx` | `0` |
| `m_checked_idx` | `0` |
| `m_start_line` | `0` |
| `m_TRIGMode` | 假设是 `0`，也就是 LT |

### 这一步要干什么

它负责：

> 从 socket 把原始 HTTP 字节流读进 `m_read_buf`

如果是 LT 模式，核心代码是：

```cpp
bytes_read = recv(m_sockfd, m_read_buf + m_read_idx, READ_BUFFER_SIZE - m_read_idx, 0);
m_read_idx += bytes_read;
```

### 假设这次全部一次读完

假设这整个 GET 请求一共 `74` 字节。

那么：

| 变量 | 值 |
|---|---:|
| `bytes_read` | `74` |
| `m_read_idx` | 从 `0` 变成 `74` |
| `m_checked_idx` | 仍然是 `0` |
| `m_start_line` | 仍然是 `0` |

含义是：

- 已经把请求读进缓冲区
- 但还没有开始解析

然后：

```cpp
return true;
```

---

## 第 4 步：`dealwithread()` 把任务交给线程池

因为 `read_once()` 成功，所以执行：

```cpp
m_pool->append_p(users + sockfd);
```

也就是把：

```cpp
users + 12
```

这个 `http_conn` 对象指针压进线程池队列。

此时线程池相关变量大致是：

| 变量 | 值 |
|---|---|
| `request` | `users + 12` |
| `m_workqueue.size()` | 假设从 `0` 变成 `1` |

然后 `dealwithread()` 会顺手延长这个连接的定时器：

```cpp
adjust_timer(timer);
```

---

## 第 5 步：线程池工作线程取出任务

工作线程在 `threadpool::run()` 里阻塞等任务：

```cpp
m_queuestat.wait();
```

现在队列里有任务了，它就取出：

```cpp
T *request = m_workqueue.front();
m_workqueue.pop_front();
```

此时关键变量：

| 变量 | 值 |
|---|---|
| `request` | 指向 `users[12]` |
| `request->m_sockfd` | `12` |
| `request->m_read_idx` | `74` |
| `request->m_checked_idx` | `0` |
| `request->m_start_line` | `0` |

在 `Proactor` 路径下，它会直接：

```cpp
request->process();
```

---

## 第 6 步：进入 `http_conn::process()`

这个函数是单连接处理总入口。

第一句就是：

```cpp
HTTP_CODE read_ret = process_read();
```

这里才真正启动 HTTP 状态机。

进入前变量仍然是：

| 变量 | 值 |
|---|---:|
| `m_check_state` | `CHECK_STATE_REQUESTLINE` |
| `m_read_idx` | `74` |
| `m_checked_idx` | `0` |
| `m_start_line` | `0` |

---

## 第 7 步：进入 `process_read()`

### 初值

```cpp
LINE_STATUS line_status = LINE_OK;
HTTP_CODE ret = NO_REQUEST;
char *text = 0;
```

所以：

| 变量 | 值 |
|---|---|
| `line_status` | `LINE_OK` |
| `ret` | `NO_REQUEST` |
| `text` | `nullptr` |

### 第一次循环：解析请求行

`parse_line()` 先切出第一行：

```http
GET /index.html HTTP/1.1
```

处理完后，假设第一行长度是 `26` 字节（含 `\r\n`）：

| 变量 | 值 |
|---|---:|
| `m_checked_idx` | `26` |
| `m_start_line` | 还没更新前是 `0` |

然后：

```cpp
text = get_line();      // 指向第一行
m_start_line = 26;
ret = parse_request_line(text);
```

`parse_request_line()` 处理后：

| 变量 | 值 |
|---|---|
| `m_method` | `GET` |
| `m_url` | `"/index.html"` |
| `m_version` | `"HTTP/1.1"` |
| `m_check_state` | `CHECK_STATE_HEADER` |
| `ret` | `NO_REQUEST` |

---

## 第 8 步：第二次循环，解析请求头 `Host`

`parse_line()` 再切出：

```http
Host:127.0.0.1:9006
```

假设这行处理完后：

| 变量 | 值 |
|---|---:|
| `m_checked_idx` | `48` |
| `m_start_line` | 更新为 `48` |

然后 `parse_headers(text)` 执行后：

| 变量 | 值 |
|---|---|
| `m_host` | `"127.0.0.1:9006"` |
| `ret` | `NO_REQUEST` |

---

## 第 9 步：第三次循环，解析 `Connection`

切出：

```http
Connection: keep-alive
```

然后：

```cpp
parse_headers(text);
```

执行后：

| 变量 | 值 |
|---|---|
| `m_linger` | `true` |
| `ret` | `NO_REQUEST` |

这表示：

> 响应发完后，这个连接可以继续复用，不必立刻关掉

---

## 第 10 步：第四次循环，遇到空行

请求头结束后有一行空行。

`parse_line()` 把它切出来后，传给：

```cpp
parse_headers(text);
```

这时：

```cpp
text[0] == '\0'
```

因为这个 GET 请求没有 body，所以：

```cpp
return GET_REQUEST;
```

随后 `process_read()` 执行：

```cpp
return do_request();
```

---

## 第 11 步：进入 `do_request()`

现在它开始做业务处理。

以静态文件为例，它会：

1. 拼接真实路径
2. `stat()` 检查文件
3. `open()`
4. `mmap()`

执行后可能得到：

| 变量 | 值 |
|---|---|
| `m_real_file` | 例如 `.../root/index.html` |
| `m_file_address` | 指向映射后的文件内存 |
| 返回值 | `FILE_REQUEST` |

---

## 第 12 步：回到 `process()`，准备进入写阶段

`process()` 收到：

```cpp
read_ret = FILE_REQUEST
```

然后调用：

```cpp
bool write_ret = process_write(read_ret);
```

这一步开始进入“组织响应”阶段。

再之后会切到：

```cpp
modfd(m_epollfd, m_sockfd, EPOLLOUT, m_TRIGMode);
```

也就是：

> 下次可写事件到来时，再真正把响应回发给客户端

---

## 这个读请求例子里最值得记住的变量变化

### 连接初始化后

| 变量 | 值 |
|---|---:|
| `m_read_idx` | `0` |
| `m_checked_idx` | `0` |
| `m_start_line` | `0` |

### `read_once()` 成功后

| 变量 | 值 |
|---|---:|
| `m_read_idx` | `74` |
| `m_checked_idx` | `0` |
| `m_start_line` | `0` |

### 请求行切完后

| 变量 | 值 |
|---|---:|
| `m_read_idx` | `74` |
| `m_checked_idx` | `26` |
| `m_start_line` | `26` |

### 所有头处理完、准备做业务时

| 变量 | 值 |
|---|---|
| `m_method` | `GET` |
| `m_url` | `"/index.html"` |
| `m_version` | `"HTTP/1.1"` |
| `m_host` | `"127.0.0.1:9006"` |
| `m_linger` | `true` |
| `m_check_state` | 已经历过 `REQUESTLINE -> HEADER` |

---

## 如果是 Reactor，区别在哪里

Reactor 路径下主要差别只有一句：

在 `dealwithread()` 里，主线程不会先 `read_once()`。

它会直接：

```cpp
m_pool->append(users + sockfd, 0);
```

然后工作线程里再调用：

```cpp
request->read_once();
request->process();
```

也就是说：

- `Proactor`：主线程先读，再交给线程池解析
- `Reactor`：主线程只分发，工作线程自己读、自己解析

但无论哪种模式，最后都会进入：

```cpp
http_conn::process_read()
```

---

## 你面试时可以怎么总结这条读链路

可以直接说：

> 客户端请求到来后，主线程先通过 `epoll_wait` 感知读事件，然后进入 `dealwithread`。在 Proactor 模式下，主线程先调用 `read_once` 把原始 HTTP 字节流读入 `m_read_buf`，此时 `m_read_idx` 增加，但 `m_checked_idx` 和 `m_start_line` 还没动。接着把连接对象投递给线程池，工作线程调用 `http_conn::process()`，其中 `process_read()` 启动 HTTP 状态机，先按 `\r\n` 切出请求行，再解析请求头，最后在请求完整时进入 `do_request()` 做资源定位或业务处理。
