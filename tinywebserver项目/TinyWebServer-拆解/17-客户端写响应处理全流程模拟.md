# 17-客户端写响应处理全流程模拟

关联笔记：
- [[TinyWebServer-面试拆解笔记]]
- [[TinyWebServer-拆解/03-入口与WebServer总控]]

## 这篇笔记讲什么

这篇只讲另一半：

> 当服务器已经准备好了响应，它是怎么把响应写回客户端的

重点变量会是：

- `m_write_idx`
- `m_iv[0]`
- `m_iv[1]`
- `m_iv_count`
- `bytes_to_send`
- `bytes_have_send`
- `m_linger`

---

## 例子：请求一个静态文件 `/index.html`

假设上一阶段 `do_request()` 已经成功找到文件，并返回：

```cpp
FILE_REQUEST
```

同时假设：

- 响应头拼完后大小是 `120` 字节
- `index.html` 文件大小是 `800` 字节

那么总共要发：

```text
120 + 800 = 920 字节
```

---

## 写链路总览

```text
http_conn::process()
-> process_write(FILE_REQUEST)
-> modfd(..., EPOLLOUT, ...)
-> epoll_wait 发现可写
-> WebServer::dealwithwrite(sockfd)
-> http_conn::write()
-> writev()
```

---

## GET 请求后的文件，到底是在什么时候发出去的

这个问题非常重要，因为很多人第一次看源码会误以为：

> `do_request()` 里既然已经 `open()`、`mmap()` 文件了，那文件是不是就在这里发出去了？

其实不是。

真正过程分成三段：

### 第 1 段：`do_request()` 只负责“找到文件并准备好”

在 `do_request()` 里，会做这些事：

1. 根据 `m_url` 拼接真实路径 `m_real_file`
2. `stat()` 检查文件是否存在
3. `open()` 打开文件
4. `mmap()` 把文件映射到内存
5. 把映射后的地址记到 `m_file_address`
6. 返回 `FILE_REQUEST`

注意：

这一步只是准备好了：

- 文件在哪里
- 文件有多大
- 文件内容在内存里的地址是什么

但它还没有真正调用 `send()` 或 `writev()`。

也就是说：

> `do_request()` 只解决“发什么”，不解决“什么时候发”。

### 第 2 段：`process_write(FILE_REQUEST)` 只负责“组织发送结构”

接下来 `process_write(FILE_REQUEST)` 会：

1. 把响应头写进 `m_write_buf`
2. 让 `m_iv[0]` 指向响应头
3. 让 `m_iv[1]` 指向 `mmap` 后的文件内容
4. 设置 `m_iv_count = 2`
5. 设置 `bytes_to_send = 响应头长度 + 文件长度`

这一步之后，服务器只是把“待发送的数据”准备成了：

- 第一段：响应头
- 第二段：文件内容

但仍然没有真正发出去。

### 第 3 段：真正发送发生在 `EPOLLOUT -> write() -> writev()`

`process()` 最后会调用：

```cpp
modfd(m_epollfd, m_sockfd, EPOLLOUT, m_TRIGMode);
```

这表示：

> 先把这个连接挂到“等可写事件”的状态

然后等下次 `epoll_wait()` 发现这个连接可写，才会走到：

```cpp
dealwithwrite(sockfd)
-> users[sockfd].write()
-> writev(m_sockfd, m_iv, m_iv_count)
```

也就是说：

> GET 请求对应的文件，真正发送的时机是在 socket 可写时，由 `write()` 里的 `writev()` 发出去的。

---

## 一句话记忆版

可以直接记成：

> `do_request()` 找文件并 `mmap`，`process_write()` 组织响应头和文件段，真正发文件是在 `EPOLLOUT` 到来后的 `writev()`。

---

## 为什么 `mmap` 的文件不会错发给别的客户端

这个问题很多人第一次看都会担心：

> 既然文件最后是 `mmap` 到一段内存地址，再通过 `writev()` 发出去，那如果另一个客户端也在请求别的文件，会不会把文件内容串掉？

结论是：

> 不会。

原因不是“地址天然安全”，而是：

> 每个客户端连接都有自己独立的 `http_conn` 对象，文件地址、目标 socket、发送进度全都保存在这个对象自己的成员变量里。

### 第 1 点：`m_file_address` 不是全局变量

`m_file_address` 定义在 `http_conn` 类内部，是成员变量，不是全局变量。

所以：

- `users[12].m_file_address` 属于 12 号连接
- `users[18].m_file_address` 属于 18 号连接

它们是两份完全独立的状态。

也就是说：

客户端 A 请求 `a.jpg`，客户端 B 请求 `b.html`，最后会分别存到：

```cpp
users[A].m_file_address
users[B].m_file_address
```

而不是共用一个地方。

### 第 2 点：发送时操作的是“当前连接对象自己的字段”

真正发数据是在：

```cpp
users[sockfd].write()
```

这一层完成的。

进入某个连接对象的 `write()` 后，它只会使用这个对象自己的：

- `m_sockfd`
- `m_iv`
- `m_iv_count`
- `m_file_address`
- `bytes_to_send`
- `bytes_have_send`

所以如果当前执行的是：

```cpp
users[12].write()
```

那么它发出去的内容一定来自：

```cpp
users[12].m_file_address
```

并且写入的目标 socket 一定是：

```cpp
users[12].m_sockfd
```

不会去碰 `users[18]` 的文件地址。

### 第 3 点：`epoll` 先告诉你“哪个 socket 可写”

主线程不会模糊地说“有个连接可写了”。

它拿到的是明确的：

```cpp
sockfd = events[i].data.fd;
```

然后再去调用：

```cpp
dealwithwrite(sockfd);
```

所以如果这次 `epoll` 返回的是：

| 变量 | 值 |
|---|---:|
| `sockfd` | `12` |

那后面只会走：

```cpp
users[12].write()
```

不会突然把 18 号连接的文件拿来发给 12 号连接。

### 第 4 点：`iovec` 也是每个连接自己的一套

很多人还会忽略一点：

不仅 `m_file_address` 是成员变量，`m_iv[2]` 也是成员变量。

也就是说：

- `users[12].m_iv`
- `users[18].m_iv`

也是两套不同的发送描述结构。

所以即使两个连接同时都在发文件：

- 12 号连接的 `m_iv[1]` 指向 12 号文件
- 18 号连接的 `m_iv[1]` 指向 18 号文件

两者不会混用。

### 第 5 点：即使两个文件地址数值“碰巧一样”，也不会串

从一般情况说，不同文件 `mmap` 得到的虚拟地址通常就不同。

但更关键的是：

即使你假设极端情况，两个时刻地址数值碰巧一样，也不会导致错发。

因为真正决定“发什么给谁”的不是裸地址本身，而是这一整组绑定关系：

```text
哪个 sockfd 可写
-> 找到哪个 http_conn 对象
-> 取这个对象自己的 m_iv 和 m_file_address
-> 写到这个对象自己的 m_sockfd
```

所以正确性依赖的是“连接上下文隔离”，而不是“地址看起来不一样”。

### 第 6 点：真正可能串的前提是什么

只有在下面这些错误设计里，才容易串：

1. 用全局变量保存文件地址
2. 多个连接共用一套 `iovec`
3. 发送时不按 `sockfd -> users[sockfd]` 取连接对象

而这个项目不是这样写的。

它的设计是：

> 每个连接一份完整状态

所以不会把别的文件错发给其他客户端。

---

## 用一个最小例子理解

假设现在有两个客户端：

### 客户端 A

- `sockfd = 12`
- 请求 `/a.jpg`

处理后：

| 变量 | 值 |
|---|---|
| `users[12].m_sockfd` | `12` |
| `users[12].m_file_address` | 指向 `a.jpg` 的映射内存 |
| `users[12].bytes_to_send` | A 的总响应长度 |

### 客户端 B

- `sockfd = 18`
- 请求 `/b.html`

处理后：

| 变量 | 值 |
|---|---|
| `users[18].m_sockfd` | `18` |
| `users[18].m_file_address` | 指向 `b.html` 的映射内存 |
| `users[18].bytes_to_send` | B 的总响应长度 |

如果这时 `epoll` 返回：

```cpp
sockfd = 12
```

那就只会调用：

```cpp
users[12].write()
```

发出去的内容就是：

- A 的响应头
- A 的 `a.jpg`

不会碰 B 的 `b.html`。

---

## 一句话总结

可以直接记成：

> `mmap` 的文件不会错发，不是因为地址本身有魔法，而是因为 TinyWebServer 给每个客户端连接都维护了一份独立的 `http_conn` 状态，文件地址、发送缓冲区、发送进度和目标 socket 全都绑定在这个连接对象里，`epoll` 返回哪个 `sockfd`，就只会操作哪个连接自己的那份数据。

---

## 第 1 步：`process_write(FILE_REQUEST)` 组织响应

`process()` 里已经得到：

```cpp
read_ret = FILE_REQUEST;
```

于是执行：

```cpp
bool write_ret = process_write(read_ret);
```

---

## 第 2 步：进入 `process_write(FILE_REQUEST)`

### 进入前，关键变量

| 变量 | 值 |
|---|---|
| `ret` | `FILE_REQUEST` |
| `m_file_stat.st_size` | `800` |
| `m_file_address` | 指向 `index.html` 的 mmap 内存 |
| `m_write_idx` | 初始假设 `0` |

### 先写状态行和响应头

它会调用：

```cpp
add_status_line(200, ok_200_title);
add_headers(m_file_stat.st_size);
```

最终效果是把这些内容写入 `m_write_buf`：

```http
HTTP/1.1 200 OK
Content-Length:800
Connection: keep-alive

```

假设拼完后：

| 变量 | 值 |
|---|---:|
| `m_write_idx` | `120` |

这表示：

> 当前响应头一共占了 120 字节

---

## 第 3 步：设置 `iovec`

接着它会做：

```cpp
m_iv[0].iov_base = m_write_buf;
m_iv[0].iov_len = m_write_idx;
m_iv[1].iov_base = m_file_address;
m_iv[1].iov_len = m_file_stat.st_size;
m_iv_count = 2;
bytes_to_send = m_write_idx + m_file_stat.st_size;
```

所以这时关键变量变成：

| 变量 | 值 |
|---|---|
| `m_iv[0].iov_base` | 指向响应头缓冲区 |
| `m_iv[0].iov_len` | `120` |
| `m_iv[1].iov_base` | 指向 `index.html` 文件内容 |
| `m_iv[1].iov_len` | `800` |
| `m_iv_count` | `2` |
| `bytes_to_send` | `920` |
| `bytes_have_send` | `0` |

这组变量的意义是：

- 第一段发响应头
- 第二段发文件内容
- 总共还有 920 字节待发

---

## 第 4 步：切到 `EPOLLOUT`

`process()` 最后会执行：

```cpp
modfd(m_epollfd, m_sockfd, EPOLLOUT, m_TRIGMode);
```

意思是：

> 响应已经组织好了，下一步等这个连接可写时真正发送

---

## 第 5 步：`epoll_wait()` 发现这个连接可写

主线程下一轮 `epoll_wait()` 返回时，发现：

| 变量 | 值 |
|---|---:|
| `sockfd` | 例如 `12` |
| `events[i].events` | `EPOLLOUT` |

于是进入：

```cpp
dealwithwrite(sockfd);
```

---

## 第 6 步：进入 `dealwithwrite(12)`

如果走 `Proactor` 路径，主线程会直接：

```cpp
users[sockfd].write()
```

如果走 `Reactor` 路径，则是把写任务丢给线程池。

这篇主模拟继续按 `Proactor` 走。

进入 `write()` 前，关键变量：

| 变量 | 值 |
|---|---:|
| `m_write_idx` | `120` |
| `m_iv_count` | `2` |
| `bytes_to_send` | `920` |
| `bytes_have_send` | `0` |
| `m_linger` | `true` 假设是长连接 |

---

## 第 7 步：第一次进入 `http_conn::write()`

先判断：

```cpp
if (bytes_to_send == 0)
```

现在：

| 变量 | 值 |
|---|---:|
| `bytes_to_send` | `920` |

所以不会直接返回。

接着执行：

```cpp
temp = writev(m_sockfd, m_iv, m_iv_count);
```

---

## 第 8 步：假设第一次 `writev()` 只发出了 300 字节

这很常见，因为内核发送缓冲区不一定一次能装下全部数据。

于是：

| 变量 | 值 |
|---|---:|
| `temp` | `300` |

然后：

```cpp
bytes_have_send += temp;
bytes_to_send -= temp;
```

更新后：

| 变量 | 旧值 | 新值 |
|---|---:|---:|
| `bytes_have_send` | `0` | `300` |
| `bytes_to_send` | `920` | `620` |

---

## 第 9 步：判断头部是不是已经发完了

判断条件：

```cpp
if (bytes_have_send >= m_iv[0].iov_len)
```

当前：

- `bytes_have_send = 300`
- `m_iv[0].iov_len = 120`

所以条件成立。

表示：

> 响应头 120 字节已经全部发完了，而且文件内容也已经发出去了一部分

于是源码执行：

```cpp
m_iv[0].iov_len = 0;
m_iv[1].iov_base = m_file_address + (bytes_have_send - m_write_idx);
m_iv[1].iov_len = bytes_to_send;
```

代入数值：

- `bytes_have_send - m_write_idx = 300 - 120 = 180`

所以变成：

| 变量 | 值 |
|---|---|
| `m_iv[0].iov_len` | `0` |
| `m_iv[1].iov_base` | `m_file_address + 180` |
| `m_iv[1].iov_len` | `620` |

含义：

> 下一次再发时，不用再发响应头了，直接从文件第 181 个字节开始继续发

---

## 第 10 步：假设第二次 `writev()` 返回 `-1` 且 `errno = EAGAIN`

这表示：

> 当前内核发送缓冲区满了，暂时写不进去更多数据

源码会走：

```cpp
if (errno == EAGAIN)
{
    modfd(m_epollfd, m_sockfd, EPOLLOUT, m_TRIGMode);
    return true;
}
```

这一步非常关键。

它不是报错退出，而是：

> 先记住当前已经发到哪里了，等下次这个连接再次可写时继续发

此时关键变量仍然保留为：

| 变量 | 值 |
|---|---:|
| `bytes_have_send` | `300` |
| `bytes_to_send` | `620` |
| `m_iv[1].iov_base` | `m_file_address + 180` |
| `m_iv[1].iov_len` | `620` |

所以：

写响应也是“断点续发”的。

---

## 第 11 步：下一次 `EPOLLOUT` 再来

主线程再次收到这个连接可写后，又会进入 `write()`。

这次不是从头发，而是沿着上次保留的变量继续。

假设这次一次性把剩余 `620` 字节都发完。

那么：

| 变量 | 旧值 | 新值 |
|---|---:|---:|
| `temp` | - | `620` |
| `bytes_have_send` | `300` | `920` |
| `bytes_to_send` | `620` | `0` |

---

## 第 12 步：全部发送完成

进入：

```cpp
if (bytes_to_send <= 0)
```

成立后会：

```cpp
unmap();
modfd(m_epollfd, m_sockfd, EPOLLIN, m_TRIGMode);
```

这表示：

1. 文件映射可以释放了
2. 这个连接重新回到“等客户端发下一次请求”的状态

如果：

```cpp
m_linger == true
```

则执行：

```cpp
init();
return true;
```

此时关键变量被重置：

| 变量 | 值 |
|---|---:|
| `bytes_to_send` | `0` |
| `bytes_have_send` | `0` |
| `m_write_idx` | `0` |
| `m_read_idx` | `0` |
| `m_checked_idx` | `0` |
| `m_start_line` | `0` |
| `m_check_state` | `CHECK_STATE_REQUESTLINE` |

这表示：

> 这个连接还活着，但已经准备好处理下一次 HTTP 请求了

如果：

```cpp
m_linger == false
```

那就返回 `false`，上层会关闭连接。

---

## 这个写响应例子里最值得记住的变量变化

### 响应头刚组织好时

| 变量 | 值 |
|---|---:|
| `m_write_idx` | `120` |
| `m_iv_count` | `2` |
| `bytes_to_send` | `920` |
| `bytes_have_send` | `0` |

### 第一次发出 300 字节后

| 变量 | 值 |
|---|---:|
| `bytes_have_send` | `300` |
| `bytes_to_send` | `620` |
| `m_iv[0].iov_len` | `0` |
| `m_iv[1].iov_base` | `m_file_address + 180` |

### 第二次发完后

| 变量 | 值 |
|---|---:|
| `bytes_have_send` | `920` |
| `bytes_to_send` | `0` |

### keep-alive 重置后

| 变量 | 值 |
|---|---:|
| `m_read_idx` | `0` |
| `m_checked_idx` | `0` |
| `m_start_line` | `0` |
| `m_write_idx` | `0` |

---

## 你面试时可以怎么总结这条写链路

可以直接说：

> 当 `do_request()` 处理完成后，`process_write()` 会先把状态行和响应头写进 `m_write_buf`，再通过 `iovec` 把“响应头”和“文件内容”组织成两段，设置 `bytes_to_send` 和 `bytes_have_send`。接着把连接切到 `EPOLLOUT`。真正可写时进入 `write()`，底层通过 `writev()` 发送。如果一次没发完，就根据 `bytes_have_send` 和 `bytes_to_send` 更新发送进度，下次 `EPOLLOUT` 再继续。全部发完后，如果是 keep-alive，就 `init()` 重置连接状态继续复用；否则关闭连接。
