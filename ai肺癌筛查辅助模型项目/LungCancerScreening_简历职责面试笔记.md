## 1. 我在这个项目里可以怎么定位自己

如果面试官问“你在这个项目里主要做了什么”，我建议这样开场：

我在这个项目里更偏系统落地侧，主要负责三块内容。

第一块是业务接口和数据处理链路，也就是把上传的 CT 文件、模型输出和前端展示串起来。

## 3. 我的存储结构是怎么设计的

这个项目的存储其实分成三层：

1. 原始 CT 文件存储
2. 数据库结构化记录存储
3. JSON 诊断详情存储

### 3.1 原始文件存储

上传接口收到 `.mhd` 和 `.raw` 后，不只是把文件读进内存做推理，还会把它们真正落盘保存。

存储目录在：

- `web_app/uploads/`

每次上传会创建一个子目录，命名方式大致是：

```text
YYYYMMDD_HHMMSS_序列名
```

例如：

```text
20260508_153000_series123/
  series123.mhd
  series123.raw
```

这样设计的好处是：

1. 一次上传对应一个独立目录，便于排查问题
2. 后面历史记录、切片展示、复查分析都能通过路径回溯到原始文件
3. 避免不同用户或不同时刻上传的同名文件相互覆盖

### 3.2 数据库存储结构

数据库核心表是：

- `Diagnosis`

在代码里对应：

- `class Diagnosis(db.Model)`

主要字段如下：

1. `id`
   主键，唯一标识一条诊断记录。

2. `filename`
   原始 `.mhd` 文件名，前端历史记录列表里会直接展示它。

3. `file_path_mhd`
   上传后保存的 `.mhd` 文件路径。

4. `file_path_raw`
   上传后保存的 `.raw` 文件路径。

5. `timestamp`
   诊断时间，默认写入当前 UTC 时间。

6. `diagnosis`
   最终诊断标签，比如：
   - `high_risk`
   - `moderate_risk`
   - `low_risk`
   - `no_nodules_found`

7. `confidence`
   一般存最可疑结节的恶性概率，方便前端列表快速展示，不必每次都去反序列化整段 JSON。

8. `result_json`
   存完整诊断结果的 JSON 字符串，这是最核心的详细报告字段。

### 3.3 result_json 里具体存什么

`result_json` 不是只存一个结论，而是存整份结构化报告，方便前端历史详情页、AI 问答和后续扩展复用。

它主要包含这些数据项，我建议你面试时直接按“字段名 + 中文含义”来讲：

1. `filename`
   中文：上传的 CT 文件名。

2. `timestamp`
   中文：本次诊断结果生成时间。

3. `total_slices`
   中文：这份 CT 一共有多少张切片。

4. `voxel_spacing`
   中文：体素间距，也就是 CT 在三个方向上的采样间隔。

5. `summary`
   中文：诊断摘要信息。

6. `nodules`
   中文：结节明细列表。

7. `support_info`
   中文：辅助说明信息，比如候选区域数量、分析说明、某些模块是否启用。

#### `summary` 里具体有什么

1. `overall_finding`
   中文：总体诊断结论。
   常见值：
   - `high_risk`：高风险
   - `moderate_risk`：中风险 / 建议进一步检查
   - `low_risk`：低风险
   - `no_nodules_found`：未发现结节

2. `nodule_count`
   中文：最终识别出的结节数量。

3. `most_concerning_nodule`
   中文：最值得关注、风险最高的那个结节的详情。

#### `most_concerning_nodule` 里具体有什么

1. `id`
   中文：结节编号。

2. `nodule_probability`
   中文：这个候选区域是结节的概率。

3. `malignancy_probability`
   中文：这个结节是恶性的概率。

4. `malignancy_level`
   中文：恶性风险等级。
   常见值：
   - `low`：低风险
   - `medium`：中风险
   - `high`：高风险

5. `center_xyz`
   中文：结节中心在病人坐标系下的位置。

6. `center_irc`
   中文：结节中心在图像数组坐标系下的位置。
   其中：
   - `index`：第几张切片
   - `row`：切片中的第几行
   - `col`：切片中的第几列

7. `diameter_mm`
   中文：估计结节直径，单位是毫米。

#### `nodules` 是什么

`nodules` 是所有结节的列表。

也就是说，`most_concerning_nodule` 只是从 `nodules` 里挑出来最值得重点展示的那个，而 `nodules` 本身保存的是所有结节的完整明细。

每个结节条目通常也会带这些字段：

1. `id`：结节编号
2. `nodule_probability`：结节概率
3. `malignancy_probability`：恶性概率
4. `malignancy_level`：风险等级
5. `center_xyz`：病人坐标
6. `center_irc`：图像坐标
7. `diameter_mm`：结节直径

#### `support_info` 里具体有什么

1. `total_candidates`
   中文：分割阶段一共提出了多少个候选区域。

2. `note`
   中文：本次分析的补充说明，比如是否是真实模型推理。

3. `malignancy_analysis_available`
   中文：恶性分析模块是否可用。

### 3.4 为什么要同时存“摘要字段”和“完整 JSON”

这是我在面试里会特别强调的设计点。

如果只存完整 JSON：

- 列表页查询不方便
- 统计聚合困难
- 简单筛选也要先反序列化 JSON

如果只存拆开的摘要字段：

- 详情丢失
- 以后扩展字段麻烦
- AI 问答和切片展示上下文不够完整

所以这里用了“摘要字段 + 完整 JSON”双层设计：

- `diagnosis`、`confidence` 这种高频展示字段单独列出来
- 完整结构化结果放进 `result_json`

这样既方便前台业务查询，也保留了完整诊断上下文。

## 4. 业务接口是怎么实现的

### 4.1 最核心接口：`POST /api/upload`

这个接口是整条业务链路的主入口。

它做的事情不是简单“上传文件”，而是完成：

1. 参数校验
2. 文件读取
3. 调用完整 AI 推理
4. 原始文件落盘
5. 结构化结果入库
6. 返回给前端展示

具体流程可以这么讲：

#### 第一步：校验上传文件

后端要求必须同时上传：

- `mhd_file`
- `raw_file`

并检查：

1. 扩展名是否正确
2. 文件名前缀是否一致

也就是说，系统不允许拿两份不匹配的 CT 元数据和体素数据去做分析。

#### 第二步：读取文件并触发推理

接口读取两个文件的二进制内容，然后调用：

- `prediction_system.process_ct_files(...)`

这一步真正把上传文件和模型推理链路连了起来。

#### 第三步：持久化原始文件

推理成功后，系统会把 `.mhd` 和 `.raw` 保存到上传目录，形成一份可追溯的原始数据归档。

#### 第四步：生成数据库记录

系统从推理结果中取出：

- 总诊断标签
- 最高恶性概率
- 完整 JSON

然后构造 `Diagnosis` 对象，写入 MySQL。

#### 第五步：返回前端

最后把推理 JSON 直接返回给前端，前端马上可以展示：

1. 总体结论
2. 最可疑结节
3. 结节列表
4. CTViewer 可视化

### 4.2 历史记录接口：`GET /api/predictions`

这个接口的职责是：

- 从数据库读取所有历史诊断记录
- 按 `id desc` 倒序返回

它会调用 `Diagnosis.to_dict()` 把数据库对象转成前端能直接消费的结构。

这是一个很关键的中间层设计，因为数据库存的是：

- 独立列
- `result_json`

而前端要的是：

- 一个完整可展示对象

`to_dict()` 正好承担了这个转换职责。

### 4.3 统计接口

这里还设计了几个面向 Dashboard 的接口，比如：

- `GET /api/statistics`
- `GET /api/diagnosis-trend`
- `GET /api/diagnosis-distribution`

这些接口本质上是把数据库中的诊断记录再做一次聚合，服务于系统级展示，不再只是单次报告展示。

### 4.4 切片展示接口：`GET /api/ct-slice/<series_uid>/<slice_ndx>`

这个接口负责把存下来的 CT 文件重新读出来，动态生成某一张切片图像，并按前端传来的结节信息画框。

也就是说，它不是静态图片下载，而是：

1. 根据 `series_uid` 找到数据库记录
2. 拿到 `file_path_mhd`
3. 重新加载 CT
4. 切出指定层
5. 叠加边界框
6. 返回 PNG

这个设计说明系统不仅保存了“结论”，也保存了“追溯和可视化所需的原始路径”。

## 5. 数据处理逻辑是怎么串起来的

### 5.1 `TumorPredictionSystem` 是总调度器

这个类的作用不是单个模型推理，而是把三阶段 AI 流程包成一个完整业务能力。

它的主流程可以概括成：

1. 加载 CT
2. 分割模型逐切片处理
3. 连通域分析生成候选区域
4. 裁 3D 小块
5. 真假结节分类
6. 良恶性分类
7. 汇总成业务 JSON

面试里我会强调：

我接手和负责的不是训练脚本层面，而是把模型输出转成业务系统可接入的数据结构。

### 5.2 为什么说我做的是“业务数据处理逻辑”

因为模型本身输出的是：

- 分割 mask
- 真假分类概率
- 恶性分类概率

这些都不是前端或者数据库能直接用的最终业务对象。

要落地成系统，需要再做一层转换：

1. 计算总体结论
2. 取最可疑结节
3. 形成结节列表
4. 附上坐标、直径、风险等级
5. 包装成统一 JSON 返回结构

也就是说，我简历里说的数据处理逻辑，核心就是把“模型输出”整理成“业务对象”。

## 6. AI 输出结果如何接入业务系统

### 6.1 AI 结果接入不是只接一个数字

这个项目里接入的是一份完整结构化报告，而不是简单“高风险 / 低风险”标签。

因为业务系统最终需要支持：

1. 上传页即时展示
2. 历史记录回查
3. Dashboard 统计
4. 切片可视化
5. 报告问答

所以 AI 输出必须设计成一份统一的结构化结果，而不是散乱字段。

### 6.2 前端怎么消费这些结果

#### Upload 页

前端调用 `/api/upload` 后，直接拿返回结果展示：

1. `summary.overall_finding`
2. `summary.nodule_count`
3. `summary.most_concerning_nodule`
4. `nodules`

这说明前后端约定的数据结构比较稳定。

#### History 页

前端调用 `/api/predictions`，拿到数据库里的历史记录，再展示：

1. 文件名
2. 诊断结果
3. 置信度
4. 时间戳
5. 详情弹窗

#### Chat 页

前端通过链接把：

- `predictionId`
- `filename`

带给聊天页面，再由聊天接口去数据库里取回该报告上下文。

## 7. 如何调用 AI 问答，以及如何降低幻觉

### 7.1 当前实现是怎么调用 AI 的

聊天接口是：

- `POST /api/chat`

它接收：

1. `message`
2. 可选的 `predictionId`

如果没有 `predictionId`，就是普通泛问。

如果有 `predictionId`，后端会：

1. 用 `Diagnosis.query.get(prediction_id)` 查数据库
2. 把该条记录转成字典
3. 从 `summary` 和 `nodules` 提取关键信息
4. 组织成上下文文本
5. 把“报告上下文 + 用户问题”一起发给通义千问

调用方式是：

- `dashscope.Generation.call(model='qwen-turbo', messages=[...])`

### 7.2 当前版本如何减少幻觉

当前实现的核心思路是**上下文约束**，不是完全自由生成。

它通过两步降低幻觉：

#### 第一步：系统提示词约束角色

系统提示词明确要求模型是：

- 专业 AI 医疗助手
- 只帮助解读肺部 CT AI 分析报告
- 回答要专业、严谨、简洁
- 最终诊断仍需执业医师做出

#### 第二步：把权威上下文拼进 prompt

真正传给大模型的，不是“随便聊肺癌”，而是：

- 文件名
- 总体发现
- 结节数量
- 最可疑结节风险等级
- 最可疑结节恶性概率
- 所有结节明细

也就是说，模型回答时是被约束在这份具体报告上下文里的。

### 7.3 这个做法为什么有效

因为模型最容易幻觉的场景，是在没有明确上下文时自由发挥。

这里通过 `predictionId -> 数据库记录 -> 结构化摘要 -> prompt` 这条链路，把模型回答绑定到了具体报告。

这样它更像“基于已知报告做解释”，而不是“凭空生成医学结论”。

### 7.4 这套方案的边界在哪里

面试里我不会说“完全杜绝幻觉”，因为那不真实。

更准确的说法是：

当前实现通过报告上下文约束显著降低了幻觉风险，但它本质上还是 prompt grounding，不是严格检索增强或规则引擎，因此仍然不能把大模型回答当成最终医学诊断。

### 7.5 如果面试官追问“怎么进一步防幻觉”

我会答几个更稳的工程化方向：

1. 只允许模型引用数据库里存在的字段，不允许自由扩展结论
2. 把回答改成模板化 / 半结构化输出
3. 在 prompt 中增加“超出报告范围就拒答”的规则
4. 给回答加字段级引用，让每句话对应报告证据
5. 把长文本上下文改成检索式拼接，而不是一次性塞整段描述

## 8. 我的数据库设计具体可以怎么讲

如果面试官问“你数据库设计具体怎么做的”，我建议你直接按下面说：

我这里不是把所有模型中间结果全拆成很多高度范式化的表，而是采用“摘要字段 + 完整 JSON + 原始文件路径”的混合存储方案。

这样设计的原因有三个：

1. 前台列表和统计页只需要高频摘要字段，查询快
2. 详情页和 AI 问答又需要完整报告上下文，所以要存完整 JSON
3. 切片可视化和问题追溯还要能回到原始 CT 文件，所以要存文件路径

这个设计兼顾了：

- 可展示
- 可追溯
- 可扩展

## 9. 我的业务接口工作可以怎么讲

如果面试官问“你具体做了哪些接口相关工作”，我建议这样答：

我主要做的是后端业务接口和前端消费结构之间的对接，重点不是单纯写一个接口壳子，而是把模型输出、文件上传、数据库记录和前端展示打成一条完整链路。

比较核心的是 `/api/upload`、`/api/predictions`、`/api/chat` 和 `/api/ct-slice` 这几类接口。

其中 `/api/upload` 负责文件校验、推理调用、结果持久化和即时返回，`/api/predictions` 负责历史记录查询，`/api/chat` 负责把报告上下文接给大模型，`/api/ct-slice` 负责切片可视化。

## 10. 联调与测试时我可以怎么讲

这部分建议你不要只说“我测了接口”，而是说“我主要定位哪些问题”。

可以这样答：

我在联调里主要关注三类问题。

第一类是上传和文件流问题，比如 `.mhd` 和 `.raw` 是否配对、路径是否正确落盘、后端是否能稳定读到完整二进制数据。

第二类是数据流转问题，比如模型输出字段和前端预期字段是否一致、数据库里摘要字段和 `result_json` 是否同步、`predictionId` 能不能把报告详情和聊天上下文串起来。

第三类是异常链路问题，比如推理失败时数据库事务是否回滚、CT 文件缺失时切片接口怎么处理、AI 问答里记录不存在时如何优雅报错。

## 11. 如果面试官问“你这部分工作的亮点是什么”

可以答：

我这部分工作的亮点不在于做了一个很复杂的单点算法，而在于把模型结果真正落成了业务系统能使用的数据和接口。

一方面是存储设计上，我做的是可展示、可追溯、可扩展的混合结构；另一方面是接口设计上，我把上传、推理、持久化、历史回查、切片可视化和问答上下文接成了一条完整闭环。这样前端不是拿到几个散乱数字，而是能真正把 AI 结果展示出来并继续交互。

## 12. 一段可以直接背的口语化回答

如果面试官问我在这个项目里具体负责什么，我会这样说：

我在这个项目里主要偏系统落地侧，负责业务接口、数据处理和数据库存储相关工作。具体来说，我把上传的 `.mhd/.raw` 文件、三阶段模型输出和前端展示串成了一条完整链路。后端这边我基于 MySQL 设计了诊断记录表，既存高频查询字段，也存完整 JSON 结果和原始文件路径，保证历史记录、统计分析、切片可视化和 AI 问答都能复用同一份数据。接口层面我重点参与了 `/api/upload`、`/api/predictions`、`/api/chat` 和 `/api/ct-slice` 这些核心接口的联调，把 AI 检测结果真正接入到业务系统里。对于 AI 问答，我做的是基于 `predictionId` 从数据库取权威报告摘要，再把上下文和用户问题一起传给大模型，尽量减少脱离报告内容的自由生成，降低幻觉风险。联调阶段我也参与定位了文件配对、字段不一致、路径回查和异常回滚这类数据流转问题。
