## 这篇笔记讲什么

这篇专门回答两个高频追问：

1. 如果多个用户同时注册同一个账号，这个项目怎么处理？
2. 如果大量用户同时注册，代码里有全局锁，会不会导致高并发下降？怎么优化？

这是面试里很常见的提问方式，因为它会从“你看懂源码了吗”进一步追到“你有没有工程优化意识”。

---

## 先说结论

当前项目的注册逻辑是：

1. 服务器启动时把 MySQL 里的用户表加载进全局 `map<string, string> users`
2. 注册时解析 POST 请求体里的用户名和密码
3. 先查 `users.find(name)` 判断用户名是否存在
4. 如果不存在，就加全局锁 `m_lock`
5. 锁内执行 `mysql_query(mysql, sql_insert)`
6. 再把用户名插入 `users`

这套实现能体现“多线程访问共享用户表需要加锁”的意识，但它不是高并发注册场景下的最优设计。

更准确地说：

> 当前写法用全局锁保护数据库插入和内存 map 更新，能降低并发写冲突风险，但会让注册链路串行化；如果注册量很大，吞吐确实会下降。更好的做法是把用户名唯一性下沉到数据库唯一索引，服务端只在更新内存缓存时加短锁，必要时使用分段锁或并发哈希表降低锁竞争。

---

## 当前项目的登录注册数据结构

源码里有两个全局对象：

```cpp
locker m_lock;
map<string, string> users;
```

含义是：

- `m_lock`
  用来保护共享用户表和注册写入逻辑
- `users`
  保存用户名到密码的映射

服务器启动时会执行：

```cpp
void http_conn::initmysql_result(connection_pool *connPool)
```

它会查数据库：

```sql
SELECT username,passwd FROM user
```

然后把结果加载进内存：

```cpp
users[temp1] = temp2;
```

所以后续登录校验主要走内存 `map`，不需要每次都查 MySQL。

---

## 登录请求是怎么处理的

登录表单是：

```html
<form action="2CGISQL.cgi" method="post">
```

服务器在 `do_request()` 里看到 URL 里带 `2`，就进入登录分支：

```cpp
else if (*(p + 1) == '2')
{
    if (users.find(name) != users.end() && users[name] == password)
        strcpy(m_url, "/welcome.html");
    else
        strcpy(m_url, "/logError.html");
}
```

登录本身只是读 `users`：

- 用户名存在
- 密码匹配

就返回 `welcome.html`。

否则返回 `logError.html`。

### 登录高并发的特点

登录是读多写少场景。

当前项目里登录不查数据库，而是查内存 `map`，所以速度很快。但严格从线程安全角度看：

- 注册线程可能正在写 `users`
- 登录线程可能同时读 `users`

标准 C++ 的 `std::map` 并不支持一边写一边无锁读。

所以工程上更严谨的做法是：

- 使用读写锁
- 登录加读锁
- 注册加写锁

这样大量登录可以并发读，只有注册写入时才短暂互斥。

## 注册请求是怎么处理的

注册表单是：

```html
<form action="3CGISQL.cgi" method="post">
```

服务器在 `do_request()` 里看到 URL 里带 `3`，就进入注册分支。

当前核心代码是：

```cpp
if (users.find(name) == users.end())
{
    m_lock.lock();
    int res = mysql_query(mysql, sql_insert);
    users.insert(pair<string, string>(name, password));
    m_lock.unlock();

    if (!res)
        strcpy(m_url, "/log.html");
    else
        strcpy(m_url, "/registerError.html");
}
else
    strcpy(m_url, "/registerError.html");
```

逻辑是：

1. 如果内存 `users` 里没有这个用户名
2. 就认为可以注册
3. 加锁
4. 插入数据库
5. 插入内存 map
6. 根据 SQL 是否成功返回不同页面

---

## 多个人同时注册同一个账号会发生什么

假设两个用户同时注册：

```text
username = alice
password = 123456
```

可能出现下面这种时间线：

| 时间 | 线程 A | 线程 B |
|---|---|---|
| T1 | 查 `users.find("alice")`，发现不存在 |  |
| T2 |  | 查 `users.find("alice")`，也发现不存在 |
| T3 | 加锁，执行 `INSERT` | 等锁 |
| T4 | 插入 `users`，解锁 | 等锁结束 |
| T5 |  | 拿到锁，也执行 `INSERT` |

这里有一个关键问题：

> 当前代码是在加锁前检查 `users.find(name)`，所以检查和插入不是一个原子操作。

因此，如果数据库没有唯一约束，理论上可能出现重复插入。

如果数据库给 `username` 加了唯一索引，那么第二个 `INSERT` 会失败，最后返回注册失败页。这个时候数据库帮我们兜住了唯一性。

---

## 当前代码还有一个小问题

当前代码是：

```cpp
int res = mysql_query(mysql, sql_insert);
users.insert(pair<string, string>(name, password));
```

也就是说，不管 SQL 插入是否成功，都会尝试把用户插入内存 `users`。

更合理的写法应该是：

```cpp
int res = mysql_query(mysql, sql_insert);
if (res == 0)
{
    users.insert(pair<string, string>(name, password));
}
```

因为只有数据库插入成功，内存缓存才应该更新。

否则可能出现：

- 数据库里没有这个用户
- 但内存 `users` 里却有这个用户

这会导致内存状态和数据库状态不一致。

---

## 为什么全局锁会影响高并发

面试官可能会这样问：

> 假设一个人注册只要 0.1 ms，但如果很多人同时注册，由于全局锁存在，不就都排队了吗？这是不是会导致高并发下降？

答案是：

是的，会下降。

因为当前锁保护的是：

```cpp
mysql_query(mysql, sql_insert);
users.insert(...);
```

这里最大的问题不是 `users.insert()`，而是 `mysql_query()`。

数据库 I/O 可能比较慢，如果把数据库操作放在全局锁里面，那么所有注册请求都会被串行化：

```text
注册请求 A 拿锁 -> 查/写数据库 -> 释放锁
注册请求 B 拿锁 -> 查/写数据库 -> 释放锁
注册请求 C 拿锁 -> 查/写数据库 -> 释放锁
...
```

这样线程池和数据库连接池的并发能力都发挥不出来。

所以这个锁适合教学项目，但不是高并发注册的最终方案。

---

## 优化方向 1：把唯一性保证交给数据库

最重要的优化是：

> 用户名是否唯一，不应该主要靠服务端内存 map 判断，而应该由数据库唯一索引保证。

可以给 `username` 加唯一索引：

```sql
ALTER TABLE user ADD UNIQUE KEY uk_username(username);
```

之后服务端可以直接执行：

```sql
INSERT INTO user(username, passwd) VALUES(...)
```

如果成功，说明注册成功。

如果失败，并且错误是 duplicate key，说明用户名已存在。

这样即使多个线程同时插入同一个用户名，数据库也会保证只有一个成功。

### 为什么数据库更适合做唯一性保证

因为数据库本来就负责：

- 索引
- 事务
- 并发控制
- 唯一约束
- 崩溃恢复

服务端内存 map 只是缓存，不应该成为最终一致性的唯一来源。

---

## 优化方向 2：缩小锁粒度

当前锁的问题是范围太大。

更好的思路是：

1. 不在全局锁里执行 `mysql_query`
2. 让不同线程通过数据库连接池并发执行 `INSERT`
3. 只有数据库插入成功后，更新内存 `users` 时加很短的锁

伪代码可以写成：

```cpp
int res = mysql_query(mysql, sql_insert);

if (res == 0)
{
    m_lock.lock();
    users.insert({name, password});
    m_lock.unlock();
    strcpy(m_url, "/log.html");
}
else
{
    strcpy(m_url, "/registerError.html");
}
```

这样锁只保护内存 map 更新，不包住数据库 I/O。

临界区从：

```text
数据库插入 + map 插入
```

缩小成：

```text
map 插入
```

吞吐会好很多。

---

## 优化方向 3：检查和插入放到同一把锁里

如果还想保留内存 map 作为注册前置判断，那么至少要把：

- `users.find(name)`
- `users.insert(...)`

放进同一个临界区。

伪代码是：

```cpp
m_lock.lock();

if (users.find(name) == users.end())
{
    int res = mysql_query(mysql, sql_insert);
    if (res == 0)
    {
        users.insert({name, password});
    }
}

m_lock.unlock();
```

这样可以避免两个线程同时通过 `find` 检查。

但是这个方案仍然有问题：

> 数据库 I/O 还在锁里，高并发注册时仍然会串行化。

所以它只是修复竞态，不是性能最优方案。

---

## 优化方向 4：使用读写锁优化登录读多写少

登录是读操作，注册是写操作。

所以可以把普通互斥锁换成读写锁：

- 登录：加读锁
- 注册成功更新缓存：加写锁

这样多个登录请求可以同时读 `users`：

```text
登录 A 读 users
登录 B 读 users
登录 C 读 users
```

它们互不阻塞。

只有注册更新 `users` 时，才需要独占写锁。

这比所有读写都用一把普通互斥锁更适合读多写少场景。

---

## 优化方向 5：分段锁或并发哈希表

如果注册量非常大，还可以继续降低锁竞争。

一种常见方式是分段锁：

```text
lock_id = hash(username) % N
```

不同用户名落到不同锁上：

```text
alice -> lock[3]
bob   -> lock[7]
tom   -> lock[1]
```

这样不同用户名可以并行注册，只有落到同一段的用户名才会竞争同一把锁。

进一步可以使用：

- `concurrent_hash_map`
- Redis 原子操作
- 数据库唯一索引 + 无状态服务端

不过面试里不一定要展开太多，重点说清楚“全局锁可以优化成更细粒度的锁”即可。

---

## 优化方向 6：缓存和数据库的一致性

这个项目里 `users` 是启动时加载到内存的。

这适合教学项目，但真实系统要考虑：

- 多台服务器时，每台机器都有自己的内存缓存
- 某台机器注册成功，其他机器缓存不知道
- 服务重启前后的状态一致性
- 数据库插入成功但缓存更新失败怎么办

所以更工程化的做法是：

1. 数据库作为最终真实数据源
2. Redis 或本地 map 作为缓存
3. 注册成功后更新缓存或删除缓存
4. 登录时优先查缓存，缓存 miss 再查数据库
5. 缓存设置过期时间，避免长期不一致

对 TinyWebServer 来说，回答到“数据库唯一索引 + 缩小锁粒度 + 读写锁”已经足够稳。

---

## 面试官追问：那如何既保证同名账号不重复，又保证高并发

可以这样回答：

> 我不会用一把全局锁把整个注册流程都串起来。账号唯一性应该交给数据库唯一索引保证，比如给 `username` 加 `UNIQUE` 约束。多个线程可以通过数据库连接池并发执行 `INSERT`，数据库会保证同一个用户名只有一个插入成功。服务端只需要根据 SQL 返回结果判断注册成功还是用户名已存在。
>
> 同时，服务端内存 `users` 只作为缓存。数据库插入成功后，我再用很短的锁更新缓存。这样锁不包住数据库 I/O，临界区很短。如果登录读很多，还可以用读写锁，让多个登录请求并发读缓存，只有注册成功更新缓存时加写锁。这样既保证一致性，也尽量保留并发能力。

---

## 面试时可以直接背的版本

> 当前项目里注册用了全局锁，能保证共享 `users` 表更新时不会被多个线程同时修改，但它确实会让注册链路串行化，尤其是锁里还包含了 `mysql_query()` 这种数据库 I/O，高并发注册时吞吐会下降。
>
> 如果优化，我会先把 `username` 加数据库唯一索引，让数据库负责最终唯一性。服务端不需要用大锁做最终判重，而是并发执行 `INSERT`，成功就注册成功，失败如果是 duplicate key 就返回用户名已存在。然后只在更新内存缓存 `users` 时加短锁，或者用读写锁、分段锁减少竞争。这样不同用户名的注册可以并发处理，同名用户名也能由数据库保证只有一个成功。
