## 索引是什么

### 简要回答

索引是帮助数据库快速定位数据的数据结构。

### 面试表达

> 索引类似书的目录，可以减少全表扫描。但索引不是越多越好，因为它会占空间，也会增加插入、删除、更新的维护成本。

## 常见索引有哪些

### 简要回答

常见分类可以按数据结构、物理存储、逻辑特性来看。

### 详细回答

按数据结构：

- B+ 树索引：最常见，适合范围查询和排序。
- 哈希索引：等值查询快，但不支持范围查询和排序。
- 全文索引：用于文本内容搜索。

按物理存储：

- 聚簇索引：数据和索引存储在一起。
- 非聚簇索引：索引和数据分开，索引指向数据位置。

按逻辑特性：

- 主键索引：唯一且不能为空。
- 唯一索引：值不能重复，通常允许空值。
- 普通索引：只加速查询。
- 联合索引：多个字段组成一个索引，遵循最左前缀原则。
- 空间索引：用于地理空间数据。

## 为什么 MySQL 常用 B+ 树

### 简要回答

B+ 树高度低、磁盘 I/O 少，叶子节点有序链表，适合范围查询。

### B 树和 B+ 树区别

- B 树非叶子节点也存数据。
- B+ 树非叶子节点主要存 key，数据集中在叶子节点。
- B+ 树叶子节点通常通过链表连接，范围查询更方便。

### 面试表达

> 数据库索引要尽量减少磁盘 I/O。B+ 树分叉多、高度低，而且叶子节点有序串联，所以点查和范围查询都比较适合。

### B+ 树优势

- 高扇出，树高低，减少磁盘 I/O。
- 非叶子节点只存 key，一个页能放更多索引项。
- 所有数据在叶子节点，查询路径长度稳定。
- 叶子节点通过链表连接，范围查询效率高。

### B+ 树限制

- 插入、删除可能引起节点分裂或合并，有维护成本。
- 索引占用额外磁盘空间。
- `LIKE '%keyword%'` 这种非前缀模糊查询通常无法利用 B+ 树索引。
- 小表上索引收益可能不明显。

## 什么时候适合建索引

### 简要回答

经常出现在 `where`、`order by`、`group by`、`join` 条件中的高选择性字段适合建索引。

### 不适合建索引

- 数据量很小的表。
- 区分度很低的字段。
- 频繁更新但很少查询的字段。
- 大字段，如很长的文本字段。

### 适合建索引的列

- `WHERE` 条件中经常使用的列。
- `JOIN` 连接列。
- `ORDER BY` 或 `GROUP BY` 中经常使用的列。
- 数据量较大的表中的高选择性字段。
- 主键、唯一约束、外键约束对应的列。

## 索引失效场景有哪些

### 简要回答

常见有不满足最左前缀、对索引列使用函数、前缀模糊查询、隐式类型转换、`or` 使用不当等。

### 详细回答

- 联合索引跳过最左字段。
- `where year(create_time) = 2026` 这种对列做函数。
- `like '%abc'`。
- 字符串字段拿数字比较。
- 范围查询后面的联合索引列利用不充分。
- 优化器认为全表扫描更划算。

### 示例

> [!tip] 记忆方式
> 索引失效的核心原因通常是：数据库没法按 B+ 树的有序结构直接定位，只能计算、扫描或放弃索引。

```sql
-- 可能失效：对索引列使用函数
-- 原因：索引里存的是 create_time 原值，不是 YEAR(create_time) 的结果。
-- 数据库需要逐行计算年份，可能无法直接利用 create_time 索引。
SELECT * FROM orders WHERE YEAR(create_time) = 2026;

-- 可能失效：前缀不确定
-- 原因：B+ 树索引按从左到右的字符顺序组织。
-- '%tom' 前面是什么不确定，无法从索引树上快速定位起点。
SELECT * FROM users WHERE name LIKE '%tom';

-- 联合索引 (a, b, c)，跳过 a 时通常无法充分利用
-- 原因：联合索引先按 a 排，再按 b 排，最后按 c 排。
-- 不给 a 条件，数据库很难直接利用 b、c 的有序性。
SELECT * FROM t WHERE b = 1 AND c = 2;
```

### 怎么改更容易走索引

| 问题写法 | 更推荐写法 | 为什么 |
|---|---|---|
| `YEAR(create_time) = 2026` | `create_time >= '2026-01-01' AND create_time < '2027-01-01'` | 不对索引列做函数，保留范围查询能力 |
| `LIKE '%tom'` | `LIKE 'tom%'` | 前缀确定时可以从 B+ 树定位起点 |
| 联合索引 `(a,b,c)` 但只查 `b,c` | 补上 `a` 条件，或新建 `(b,c)` 索引 | 遵循最左前缀原则 |

```sql
-- 推荐：把函数计算改成范围查询
-- create_time 索引可以按时间范围快速定位
SELECT * FROM orders
WHERE create_time >= '2026-01-01'
  AND create_time < '2027-01-01';

-- 推荐：前缀匹配，name 索引可能生效
SELECT * FROM users WHERE name LIKE 'tom%';

-- 推荐：联合索引 (a, b, c) 从最左列 a 开始使用
SELECT * FROM t WHERE a = 1 AND b = 1 AND c = 2;
```

### 面试表达

> 索引失效不是“索引坏了”，而是 SQL 写法让优化器无法高效利用索引结构。排查时我会先看索引定义，再用 `EXPLAIN` 看执行计划，重点关注是否全表扫描、扫描行数、是否使用临时表和排序。

## 聚簇索引和非聚簇索引有什么区别

### 简要回答

聚簇索引的叶子节点直接存放数据行，非聚簇索引的叶子节点通常存放主键值或数据地址。

### 详细回答

InnoDB 的主键索引是聚簇索引，数据行和主键索引组织在一起。二级索引通常是非聚簇索引，叶子节点保存索引列和主键值，查到主键后可能再回表查询完整数据。

### 面试表达

> 聚簇索引决定数据的组织方式，所以一张 InnoDB 表通常只有一个聚簇索引；二级索引查完整数据时可能需要回表。
