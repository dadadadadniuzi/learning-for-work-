## 互斥锁与自旋锁

### 简要回答

- 互斥锁：抢不到锁时线程会阻塞挂起，让出 CPU
- 自旋锁：抢不到锁时线程不挂起，而是持续循环等待

也可以这样记：

- 自旋锁：忙等换低延迟
- 互斥锁：睡眠换省 CPU

### 详细回答

#### 1. 自旋锁是什么

自旋锁的核心机制是：

- 线程抢不到锁时不睡眠
- 而是在用户态不断循环检查锁状态

它通常基于原子操作实现，例如 `atomic_flag`。

```cpp
#include <atomic>

class Spinlock {
private:
    std::atomic_flag flag = ATOMIC_FLAG_INIT;

public:
    void lock() {
        while (flag.test_and_set(std::memory_order_acquire)) {
            // busy-wait
        }
    }

    void unlock() {
        flag.clear(std::memory_order_release);
    }
};
```

#### 2. 互斥锁是什么

互斥锁 `mutex` 的核心机制是：

- 抢不到锁时线程会阻塞
- 由操作系统调度挂起
- 等锁可用时再唤醒继续运行

它的本质是：

- 用上下文切换换 CPU 资源节省

```cpp
#include <mutex>

std::mutex mtx;

void func() {
    std::lock_guard<std::mutex> lock(mtx);
    // 临界区
}
```

#### 3. 两者的核心区别

| 对比点 | 自旋锁 | 互斥锁 |
|---|---|---|
| 等待方式 | 忙等待，不断轮询 | 阻塞挂起，等待唤醒 |
| CPU 消耗 | 高 | 低 |
| 上下文切换 | 没有或较少 | 有 |
| 响应延迟 | 低 | 相对更高 |
| 适合场景 | 极短临界区、低竞争、多核 | 临界区较长、高竞争、用户态程序 |

#### 4. 为什么自旋锁有时更快

如果锁持有时间非常短，那么：

- 线程刚挂起又被唤醒

这件事本身的上下文切换开销，可能比“原地转几圈”等待锁释放更贵。

所以在：

- 临界区极短
- 核数足够
- 竞争不激烈

这些条件下，自旋锁可能更划算。

#### 5. 为什么互斥锁更稳

如果锁持有时间稍长，自旋线程就会白白烧 CPU。

这时互斥锁更合适，因为它会把线程挂起，让 CPU 去做别的事，避免无意义忙等。

所以互斥锁更适合：

- 长临界区
- 高竞争
- 单核
- 功耗敏感场景

### 代码示例

#### 自旋锁示例

```cpp
#include <atomic>
#include <iostream>
#include <thread>
using namespace std;

class Spinlock {
private:
    std::atomic_flag flag = ATOMIC_FLAG_INIT;

public:
    void lock() {
        while (flag.test_and_set(std::memory_order_acquire)) {
            // 可选：std::this_thread::yield();
        }
    }

    void unlock() {
        flag.clear(std::memory_order_release);
    }
};

Spinlock spinlock;
int shared_data = 0;

void spinlock_worker(int id) {
    for (int i = 0; i < 1000; ++i) {
        spinlock.lock();
        shared_data++;
        spinlock.unlock();
    }
    std::cout << "Thread " << id << " finished" << std::endl;
}
```

#### 互斥锁示例

```cpp
#include <iostream>
#include <mutex>
#include <thread>
using namespace std;

std::mutex mtx;
int shared_data = 0;

void mutex_worker(int id) {
    for (int i = 0; i < 1000; ++i) {
        std::lock_guard<std::mutex> lock(mtx);
        shared_data++;
    }
    std::cout << "Thread " << id << " finished" << std::endl;
}
```

### 适用场景

#### 自旋锁适用场景

1. 多核处理器系统
2. 临界区非常短
3. 低竞争场景
4. 实时性要求高，不能容忍调度延迟
5. 内核或底层系统场景中不方便睡眠

#### 互斥锁适用场景

1. 单核系统
2. 临界区较长
3. 高竞争场景
4. 用户态程序
5. 功耗敏感场景

### 面试官可能追问

#### Q1：为什么单核 CPU 上通常不建议使用自旋锁？

因为单核上如果线程 A 持有锁，线程 B 一直自旋占着 CPU，那么 A 反而更难拿到时间片去释放锁，等于大家都在空耗。

#### Q2：自旋锁会不会引起活锁？

可能。

多个线程在高竞争下都疯狂抢锁，虽然系统没有“睡死”，但谁都迟迟拿不到锁，整体效率会很差。实际中会通过退避、让出 CPU、票据锁等方式缓解。

#### Q3：如何确定自旋次数上限？

它通常要结合：

- 上下文切换成本
- 临界区平均长度
- CPU 核数
- 竞争强度

很多工程实现会采用自适应策略，而不是写死次数。

### 面试短答

> 自旋锁和互斥锁的本质区别在于等待方式。自旋锁抢不到锁时不睡眠，而是在用户态循环等待，所以避免了上下文切换，适合极短临界区和低竞争场景；互斥锁抢不到锁时会阻塞挂起，让出 CPU，适合临界区较长、高竞争或用户态程序。简单说，自旋锁是用 CPU 换延迟，互斥锁是用调度切换换 CPU 节省。

## select poll 和 epoll

### 简要回答

- `select`：最早的 I/O 多路复用方式，有 fd 数量上限
- `poll`：去掉了 `select` 的固定上限，但仍然需要线性遍历
- `epoll`：事件驱动，只返回就绪 fd，更适合高并发

这三者的共同目标都是：

> 让一个线程同时监听多个文件描述符，谁就绪了就处理谁。

区别主要在于：

- fd 集合怎么保存
- 内核怎么通知就绪事件
- 程序是否要遍历全部 fd

### 详细回答

#### 1. select

`select` 是最早的 I/O 多路复用机制之一。

它使用：

- `fd_set`

也就是位图结构来表示需要监听的文件描述符集合。

典型特点：

1. 默认有 fd 数量上限，常见是 `FD_SETSIZE = 1024`
2. 每次调用前都要重新设置监听集合
3. 返回后还要遍历整个集合，检查哪些 fd 就绪
4. 时间复杂度通常是 `O(n)`

```cpp
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(sockfd, &readfds);

struct timeval tv;
tv.tv_sec = 5;
tv.tv_usec = 0;

int ret = select(sockfd + 1, &readfds, NULL, NULL, &tv);
if (ret > 0) {
    if (FD_ISSET(sockfd, &readfds)) {
        // 处理可读事件
    }
}
```

#### 2. poll

`poll` 可以看作对 `select` 的一次改进。

它不再用位图，而是使用：

- `pollfd` 结构数组

来保存监听的文件描述符和感兴趣的事件。

典型特点：

1. 没有 `select` 那种固定 1024 的硬性上限
2. 但仍然需要遍历整个数组，检查谁就绪
3. 每次调用时，仍然要把描述符数组传给内核
4. 时间复杂度通常仍是 `O(n)`

```cpp
struct pollfd fds[1];
fds[0].fd = sockfd;
fds[0].events = POLLIN;

int ret = poll(fds, 1, 5000);
if (ret > 0) {
    if (fds[0].revents & POLLIN) {
        // 处理可读事件
    }
}
```

所以 `poll` 主要解决的是：

- `select` 的描述符数量上限问题

但并没有从根本上解决“每次都要线性遍历”的性能问题。

#### 3. epoll

`epoll` 是 Linux 特有的高性能 I/O 多路复用机制。

它的核心思路不再是“每次把全部 fd 重新交上去并遍历一遍”，而是：

1. 先把感兴趣的 fd 注册进内核
2. 内核维护这批 fd
3. 等就绪事件发生时，直接把就绪列表返回给用户态

典型接口有三个：

1. `epoll_create1`
2. `epoll_ctl`
3. `epoll_wait`

```cpp
int epfd = epoll_create1(0);
struct epoll_event ev, events[10];
ev.events = EPOLLIN;
ev.data.fd = sockfd;

epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &ev);

int nfds = epoll_wait(epfd, events, 10, 5000);
for (int i = 0; i < nfds; i++) {
    if (events[i].data.fd == sockfd) {
        // 处理可读事件
    }
}
```

### 三者的核心差异

| 对比点 | `select` | `poll` | `epoll` |
|---|---|---|---|
| 数据结构 | `fd_set` 位图 | `pollfd` 数组 | 内核维护关注集合 + 就绪队列 |
| fd 数量限制 | 有，常见 1024 | 没有固定小上限 | 通常更适合大量 fd |
| 每次是否重传集合 | 是 | 是 | 否，注册后由内核维护 |
| 是否遍历全部 fd | 是 | 是 | 不需要，直接拿就绪列表 |
| 复杂度直觉 | `O(n)` | `O(n)` | 就绪事件处理更接近事件驱动 |
| 适合场景 | 小规模、兼容性需求 | 中等规模、跨平台需求 | Linux 高并发服务器 |

### 为什么 epoll 更高效

这是最常见追问。

可以从四点答：

1. `epoll` 更像事件驱动，不是每次都轮询全部 fd。
2. 监听集合注册一次后由内核维护，不需要每轮都把全部集合重新复制进去。
3. `epoll_wait` 直接返回就绪列表，不需要遍历一大堆不活跃连接。
4. 在高并发场景里，它只关注“活跃连接”，所以性能不会像 `select/poll` 那样随着总连接数线性恶化。

### LT 和 ET

`epoll` 支持两种触发模式：

#### LT：水平触发

只要 fd 仍然处于就绪状态，就会反复通知。

特点：

- 编程简单
- 不容易漏数据
- 默认模式

#### ET：边缘触发

只在状态发生变化时通知一次。

特点：

- 效率更高
- 但编程更复杂
- 一般要配合非阻塞 I/O，一次性把数据尽可能读完或写完

一句话记：

- LT：只要有数据，持续提醒你
- ET：只在“来了新变化”时提醒一次

### 性能对比怎么讲

连接数少时：

- 三者差距通常不明显

连接数大时：

- `select/poll` 因为要线性遍历所有 fd，性能明显下降
- `epoll` 基本只处理就绪连接，扩展性更好

### 适用场景

#### select / poll

适合：

1. 跨平台程序
2. 连接数不多
3. 对 Linux 特有接口依赖不强

#### epoll

适合：

1. Linux 平台
2. 高并发服务器
3. 长连接场景
4. 大量 socket 监控

### 面试官可能追问

#### Q1：为什么 epoll 比 select / poll 更高效？

因为 `epoll` 更像事件驱动：内核维护关注集合，并直接返回就绪列表，而不是每次把全集合重新交上去再线性遍历所有 fd。

#### Q2：epoll 的 LT 和 ET 模式有什么区别？如何选择？

- LT：持续通知，简单稳妥，默认常用
- ET：只在状态变化时通知一次，效率更高，但更容易写错

一般：

- 默认优先 LT
- 明确追求高性能且能正确处理非阻塞逻辑时，再考虑 ET

#### Q3：epoll 是如何实现高性能的？

核心原因：

1. 关注集合注册后由内核维护
2. 活跃连接进入就绪队列
3. `epoll_wait` 直接返回活跃 fd

高并发场景下，它避免了对全部连接的无效扫描。

#### Q4：select 的 1024 限制可以改吗？

理论上可以通过修改 `FD_SETSIZE` 和相关配置去调大，但不推荐。因为这只是缓解，不是根治，面对大规模连接时更合理的方案还是 `poll` 或 `epoll`。

### 面试短答

> `select`、`poll` 和 `epoll` 都是 I/O 多路复用机制，目标是让一个线程同时监听多个 fd。`select` 最早，使用位图，有 1024 左右的 fd 上限；`poll` 用数组去掉了这个硬上限，但仍然要线性遍历；`epoll` 是 Linux 高性能方案，采用事件驱动思路，先把 fd 注册进内核，再由 `epoll_wait` 直接返回就绪列表，所以更适合高并发场景。`epoll` 还支持 LT 和 ET 两种触发模式，默认 LT 更稳，ET 性能更高但编程复杂。
